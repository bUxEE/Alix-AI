# AlixAI security test backlog

- **Task:** M0-14 (initial version, written before any code exists)
- **Companion documents:** [threat-model.md](threat-model.md), [localai-hardening-checklist.md](localai-hardening-checklist.md)

Every threat the design says must be tested has at least one numbered `SEC-NNN` entry below.
Each entry names the threat, the component that carries the control, the test that proves the
control, the build task that owns that test, a severity and how it is verified. The last sections
map every §16.4 bullet and every §12.6 case back to its entries, list who owes what, and record the
places where the build plan did not yet contain the control the test would need.

## 1. Rules for this file

1. **IDs are stable.** `SEC-NNN` is exactly three digits. Never renumber and never reuse an id. A
   retired threat keeps its row and starts its Threat cell with `RETIRED:`. New threats take the next
   free number at the end of the last table.
2. **One definition per id.** An id is defined exactly once, in the first column of a table row in
   section 4. Every other mention (matrices, indexes, tests) only refers to it.
3. **Machine-read.** `tests/security/cmd/coverage` (M5-08) parses the section 4 rows with the
   pattern `^\| (SEC-\d{3}) \|` and the fixed column order below. Do not reorder or merge columns.
4. **A test is covered** when its entry in the `Test(s)` column resolves to an existing Go test
   function in the named package, or the test carries the tag `// SEC-NNN` in a comment directly above
   the function (preferred for new tests, mandatory for `(new)` entries). One test may carry several
   tags; one id may have several tests. Rows with Kind `pentest` or `human` are covered when the
   named report records a result for the id (see section 6).
5. **Test names.** Names in the `Test(s)` column that belong to another task are quoted from that
   task's acceptance list in the build plan and must exist with exactly those names. Names
   marked `(new)` are proposals owned by M5-08 (or by the task named in `Owner`); the owner may rename
   them but must keep the SEC tag. Where a row says `(extend)`, the existing test is not enough on its
   own and the owner adds the case described in `Required test`.
6. **Fail-closed expectation.** Unless a row says otherwise, "rejected" means a typed `ErrCode` from
   `pkg/contracts`, zero calls to any adapter `Prepare`/`Commit`, an audit event, and no
   success-looking response.
7. **Fixtures.** Tests use generated test keys and synthetic data. No real secrets, no real
   personal data.

### Columns

| Column | Meaning |
| --- | --- |
| ID | `SEC-NNN` |
| Threat | What the attacker does or what fails |
| Ref | Section of the internal design document the threat comes from (`additive` marks external provider mode); kept for traceability |
| Component (control task) | The component that carries the control and, in brackets, the task that builds it |
| Required test | What the test must assert, concretely enough to write without re-reading the design |
| Test(s) | `package-dir: TestName, TestName` entries separated by `;`. `(new)` marks a test that does not exist in any task yet |
| Owner | Task(s) whose deliverable includes the test. First task listed writes it; later tasks extend it |
| Sev | Severity, see below |
| Kind | `automated` (runs in `go test`/CI), `pentest` (internal grey-box test, M5-12), `human` (external review or signed evidence, M6-H01 or an M5-H task). `automated+pentest` means CI covers the control and M5-12 probes it live |

### Severity scale

| Severity | Definition | Release effect |
| --- | --- | --- |
| Critical | Directly breaks a §23 release gate: cross-tenant disclosure, unauthorized, replayed or duplicated commit, model-driven scope or tool expansion, forged identity, activation of an unaudited application | Blocks release (gate 14); no waiver |
| High | A control that prevents a Critical outcome fails open under one further fault; secret disclosure; code execution or host compromise; loss of audit or supply-chain integrity | Blocks release (gate 14); no waiver |
| Medium | Availability loss, bounded information disclosure, degraded correctness that is labelled to the user, or missing defence in depth | Must be fixed or accepted in writing by the maintainers before the public beta |
| Low | Theoretical exposure or a side channel that is accepted and documented | Tracked; no release effect |

## 2. Naming convention for new tests

New tests live under `tests/security/<area>/` (areas: `injection`, `isolation`, `identity`,
`actions`, `adapters`, `packages`, `runtime`, `localai`, `dos`, `local`, `secrets`, `audit`,
`supplychain`, `posture`, `rag`). Function names start with `TestSec`, carry the tag
`// SEC-NNN` and describe the behaviour, for example
`// SEC-034` above `func TestSecReplayedTokenRejectedAcrossRestart`. M2-13 already fixes the
`TestSecRAG*` names for the RAG area.

## 3. Reading the owner column

Most controls are built and unit-tested by the milestone task that creates the component. Those
tests are the primary evidence, and this file points at them rather than duplicating them. M5-08
adds the tests that cut across components (end-to-end, fuzzing, static checks of deployment files,
secret scans) and checks that no id is left without a test. M5-12 probes the running stack. Items
that need an independent party or signed human evidence say so in the Kind column.
