# Efficiency review — M1-14: dialogue engine v1, the §11.1 turn pipeline

Every feature records this before it counts as done.

All timings and allocation figures were measured on the Windows 11 dev box (Intel i7-10700K,
16 logical CPUs) with Go 1.27, `CGO_ENABLED=0`, SQLite (`modernc.org/sqlite`) on the box's temp
disk, and are labelled **dev box**: they are not from a resource-limited container, so they are
neither **emulated** nor **certified**. Timings are `go test -bench` means (three runs of 300
iterations; the ranges are over those runs), not percentiles. **No model runs in this task**: the
provider is the deterministic fake, so every figure about inference is either a size in tokens
(computed from real built prompts) or an **estimate from arithmetic, not a measurement**, and each
is labelled so. Token figures use `providers.EstimateTokens` (one token per three bytes), which
overestimates English and Italian by roughly a third; the "at 4 bytes per token" figure beside it
is the usual real-tokenizer ratio and is **also an estimate**: there is no tokenizer on the box and
no model whose tokenizer could be measured (M0-13 and the M1 corpus runs are where that is settled).

Repeat the measurements:

```
go test -count=1 -run TestPromptSizesForTheEfficiencyReview -v ./internal/dialogue/   # prompt sizes
go test -run xxx -bench . -benchmem -benchtime 300x -count 3 ./internal/dialogue/     # pipeline cost without inference
go test -count=1 ./internal/dialogue/... ./internal/sessions/...                      # 133 passing tests and subtests
```

## Requirement
The turn pipeline of §11.1 from scope check to verified response, with the model used only where
only a model can do the job: map free text to a typed `TaskProposal`, and phrase a directive.

- the model sees only the shortlisted capabilities' visible fields, the goal and slots, the last
  question and a bounded window of recent turns; never a token, a credential, another tenant's text,
  the full transcript or an unbounded tool list (rules 6 and 10; SEC-001, SEC-002, SEC-029);
- text from the user, the host and retrieved sources is fenced as labelled data and never placed in a
  system message (§12.6; SEC-007);
- the prompt, the output constraint included, stays inside a token budget that is enforced before the
  runtime is called, and a budget violation is `validation_failed`, not retryable (§17.2; SEC-076);
- a model that is unavailable, slow or wrong is a clear typed failure with nothing executed; a
  malformed or partial proposal is `schema_invalid` and is never partially trusted (§18; SEC-010);
- the response is the model's text only if the verifier accepts it, otherwise the template for the
  same directive, and always the template when no model is available (§11.1, §18);
- the whole thing must fit the Lite profile and keep the 4 GB direction possible (rules 12, 16, 17):
  no extra resident model, no always-on service, bounded context, bounded memory per session.

## No-model / deterministic option
Used first, everywhere it is exact, and the model is called only for what it alone can do. The
pipeline decides without a model:

| Step | How | Model calls it saves |
|---|---|---|
| scope and rate checks, session lookup and expiry | verified `Scope`, `identity.CheckContinuity`, a sliding-window limiter, goal TTL | 0 (never a model step) |
| capability shortlist | `capabilities.Router`: policy exposure, active goal and its next actions, terminology and title words (M1-08) | all, for a request outside the application: out-of-scope is a refusal with **no model call** |
| exact cases | an exact help request ("what can you do", "aiuto") is answered from the policy-exposed capabilities | the proposal call |
| a read that takes no fields | one decisive candidate, level 0, nothing to confirm, no required or visible field: the proposal is built by code | the proposal call |
| choosing among host candidates | a selected choice ID is applied to the pending clarification | the proposal call |
| confirm, reject | structured inputs from the client UI; the token is never read by a model | the proposal call |
| entity resolution | an adapter Read, never the model | n/a |
| validation of every proposed value | the capability's own field definitions (type, range, length, enum, date, duration) | n/a |
| directive, preparation, commit, receipt | `internal/actions`, host results | n/a |
| response for refusals, failures, step-up, cancellation, no-evidence | the deterministic template (`TemplateOnly`, default) | the response call |

What remains for a model is exactly two jobs: extracting typed field values from free text
(call 1) and phrasing a directive naturally (call 2). Call 2 is optional per act: `Config.TemplateOnly`
can name every act, which gives a one-model-call-per-turn pipeline with plainer wording and the same
facts. Chosen default: verbalise the acts where conversational phrasing matters (`present_result`,
`report_outcome`, `ask_missing`, `ask_invalid`, `disambiguate`, `request_confirmation`, `offer_help`)
and use the template for the rest.

## Decision
The deterministic pipeline of this task with **two model calls at most per turn**, both to the one
controller role, and the Lite prompt budget below.

**Prompt sizes of typical turns** (estimated tokens, `providers.EstimateTokens`; about = at 4 bytes
per token, an estimate). The proposal prompt includes the output constraint, which the budget counts.

| Turn | Est. toks | Bytes | About |
|---|---|---|---|
| proposal, demo app (2 capabilities), a read | 763 | 2,262 | 570 |
| proposal, demo app (2 capabilities), a write | 871 | 2,547 | 640 |
| proposal, 5 capabilities, no history, English | 1,076 | 3,200 | 800 |
| proposal, 5 capabilities, goal and 4 turn rows, English | 1,272 | 3,724 | 930 |
| proposal, 5 capabilities, goal and 4 turn rows, Italian | 1,290 | 3,777 | 944 |
| proposal, 2 capabilities after a decision-stage selection | 887 | 2,632 | 660 |
| response, `present_result` (one fact) | 334 | 978 | 245 |
| response, `request_confirmation` | 369 | 1,083 | 270 |
| response, `report_outcome` | 330 | 964 | 240 |

Reading the table: a fixed part of about 760 est. toks (system rules, the constraint skeleton, the
date, the user's message), about 63 est. toks per shortlisted capability (title, purpose sentence,
visible fields, terms, the constraint's field names), about 200 est. toks for a goal and a four-row
window. A typical read or write turn therefore costs about 1,100 est. toks in and about 60 out for
both calls together; an out-of-scope request costs 0.

**Lite context budget (proposed for `docs/operations/resource-budgets.md`, which does not exist yet):**
prompt at most **2,048 est. toks** (about 1,500 real tokens; `Config.MaxPromptTokens`), output at most
**256 toks** per call (`MaxProposalTokens`, `MaxResponseTokens`), shortlist at most 5 (the router's
default, 12 hard), replay window 6 turn rows of at most 240 runes, user text at most 1,000 runes. That
is 2,304 est. toks of context per request, which leaves room in a 4,096-token context for the
runtime's own template overhead. The estimator overestimates, so the real margin is larger. Over
budget the builder cuts in a fixed order (oldest turns, then offered choices, then the lowest-ranked
capabilities) and never widens; if the minimum does not fit the call is not made. This is enforced
twice: by the builder, and again by `providers.WithBudget` at the runtime boundary.

Choices the plan left open, recorded for the ADR owner:

- **Confirmation is a structured turn input**, not a model reading of "yes". `Turn` takes a
  `Confirmation{PreparationID, Token}` from the client UI; the token never reaches a prompt, the
  session state, a log or an audit event.
- **Level 0 and 1 with confirmation mode none commit in the same turn**, after `Prepare`, through the
  coordinator (which asks the policy gateway again). Level 2 asks, level 3 sends the user to the
  application's own UI (`request_step_up`); the AI path never completes a step-up.
- **Entity resolution is an adapter Read** with the reserved arguments `entity_type`, `mention` (and
  `candidate_id`), because the AppAdapter contract has no resolve operation and the package schema
  only declares one per entity type. `EntityResolver` is a seam; the default is documented in
  `entity.go`. M1-10 and M1-17 must map the reserved read to the declared resolver.
- **The model's proposal is a candidate, never an instruction:** the capability must be on the
  shortlist the model was offered, policy must allow it, every value is validated against the
  capability's field definitions, fields the policy withholds are dropped, and `TaskFields` (which
  sensitive fields the task needs) is decided from the package, never by the model.
- **No retry of a malformed proposal.** One model call, validated; a second attempt would double the
  cost of every bad output for a gain that is not measured. Reopen with corpus data.
- **`dialogue.turn` audit event** (identifiers, act, code, call sizes, never text) is written before
  the turn's state is saved and fails closed like the policy and action events: a turn that cannot be
  audited is not acknowledged (after a commit, `Turn` returns the result with its receipt and the error).

## Resource impact
**Dev box**, model replaced by the instant fake, SQLite with `synchronous=NORMAL`, the real audit log
and policy gateway wired (every policy decision is an audit append):

| | Mean (3 runs of 300) | Allocation per op |
|---|---|---|
| `BenchmarkTurnRead`: scope, session, route, proposal, validate, Read, directive, verify, persist, audit | 9.2 to 10.8 ms | 0.87 MB, 17.5 k allocations |
| `BenchmarkTurnWriteAndConfirm`: a prepare turn and its confirmation turn (Prepare, Confirm, Commit, receipt) | 17.0 to 22.1 ms | 1.37 MB, 26.1 k allocations |
| `BenchmarkBuildProposal`: five capabilities, four turn rows | 65 to 75 us | 28 KB, 191 allocations |

Where the time goes (CPU profile of the read benchmark): about **50 percent is the audit appends of
policy decisions** (`Gateway.Decide` writes one event per decision through its sink, each a SQLite
transaction), the router's `Expose` is about 31 percent of the turn, `Coordinator.Read` about 12
percent, and the builder, validation and verifier are below measurement noise. A read turn on a package
with three declared capabilities writes five `policy.decision` events (about 1.65 KB each) and one
`dialogue.turn` event (about 230 B). **This scales with the catalogue:** `Expose` decides every declared
capability, so a package with 100 capabilities appends about 100 policy events per turn through the
sink (about 150 ms of SQLite time on this box, an extrapolation from 1.5 ms per decision, not measured
at that size). M1-08's figure of about 4.3 ms for routing at 100 capabilities was without a sink. The
fix belongs to the gateway and the composition root (append denials and the decisions that matter for
audit, batch or sample the rest); it is reported, not changed here.

Latency against inference: the deterministic pipeline adds about 10 to 22 ms to a turn whose model
calls are expected to take hundreds of milliseconds to seconds on the Lite profile (**estimate, not
measured**), so it is not the bottleneck.

Storage: a session is one row of about 640 B (scope and state) plus at most 40 turn rows (clipped at
2,000 runes each, pruned), so at most about 80 KB in the worst case and a few hundred bytes in a typical
short session; the demo scenario above stored five turn rows of 181 bytes in total. Audit adds about 5
policy events and one turn event per turn (about 8 KB for a three-capability package).

Memory: no resident state beyond the sessions in SQLite, the per-session lock table (an entry exists
only while a turn runs), and the rate limiter, which keeps at most 4,096 principals with at most 60
timestamps each (24 B per timestamp, at most about 5.9 MB in the worst case; a handful of KB in a
real deployment) and evicts idle keys.

Concurrency: turns of one session are serialised (one model call in flight per session); different
sessions run in parallel, bounded by the adapter wrapper's in-flight limit and the model runtime. The
decision stage is bounded by a 250 ms deadline and a panic or a hang is a fallback.

## 4 GB profile impact
**Preserves** the 4 GB direction; it does not make it harder, and nothing here is evidence that 4 GB
works (that remains aspirational until the full workload passes its gates).

- No new resident model, process or listener: both calls go to the one controller role, so there is
  no model duplication. A deployment that runs the template-only configuration needs one model call
  per turn.
- Context is bounded by construction: at most 2,048 est. toks in and 256 out per request, a 6-row
  replay window, a shortlist of at most 5 (12 hard) and a 1,000-rune user message, so the KV cache a
  request needs is small and does not grow with conversation length or catalogue size.
- Per-turn heap is transient (under 1.4 MB allocated) and the long-lived state is one SQLite row per
  session and a bounded limiter map.
- The risk that is not a memory risk: the audit write amplification of policy decisions above.
  It costs CPU and disk I/O on a small host, not RAM, and is flagged for the gateway owner.

## Re-evaluation trigger
- The first run of the M1 conversation corpus against a real controller model (M0-13 and later): replace
  the estimated tokens with the runtime's own counts (`ModelCall.TokIn`/`TokOut` are recorded for this),
  settle `MaxPromptTokens`, and decide whether a second attempt after a malformed proposal pays for
  itself.
- The decision stage of milestone D: re-measure how many proposal calls it avoids, and the prompt size
  when it narrows the shortlist to one capability (887 est. toks against 1,076 for five).
- Replacement of the minimal session state and the replay window by M3-01 and M3-03, and the RAG evidence
  of M2-10 entering the prompt (its budget is separate and must be added to this one).
- A package with more than about 20 declared capabilities, or the first run with the audit sink on a
  catalogue of that size: re-measure the policy-event cost of `Expose`.
- A new language pack: a language whose bytes per token differ from English and Italian changes the
  estimate, and its templates change the response prompts.
