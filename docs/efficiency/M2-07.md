# Efficiency review — M2-07: VectorIndexProvider and the embedded vector index

Every feature records this before it counts as done. The decision
itself is [ADR 0011](../decisions/0011-embedded-vector-index.md); this file holds the evidence.

## Requirement
Semantic retrieval over chunk embeddings for the hybrid query pipeline (§12.4), behind a replaceable
`VectorIndexProvider`, inside the minimum deployment (§5.1: no external vector database, no new
always-on process). The embedding model is Granite Embedding 97M Multilingual R2, 384 dimensions.

What it must meet, from ADR 0011:

- **Quality:** recall@10 of at least 0.95 against an exact float64 brute force.
- **Latency:** p95 of at most 150 ms at the supported corpus ceiling on emulated Lite (4 CPU).
- **Safety:** scope (application, tenant, workspace) is applied to what is read, before any similarity
  is computed (SEC-021); embedding reuse is scoped so it is not a cross-tenant existence oracle
  (SEC-023); a delete removes the vectors.
- **Footprint:** bounded RAM, pure Go with `CGO_ENABLED=0`, derived and rebuildable data, embedding
  work as queued class-5 jobs that yield to interactive work (§3 rules 12 and 13).

## No-model / deterministic option
Two levels, smallest first.

1. **No vectors at all: FTS5/BM25 only.** It is the degraded mode the query pipeline already has
   (labelled `reduced_semantic_recall`, M2-09). Cost: zero extra RAM, storage, CPU or embedder calls.
   It finds exact terms and identifiers and cannot find a paraphrase or a question in another
   language, which is why §12.4 lists a vector stage at all. How much recall the vector stage adds on
   a real corpus is **not measured here**: it needs the embedder and a labelled corpus, and this task
   is hermetic (no model, no network). That measurement is owed to M2-14 (harness) and M2-15 (live,
   Granite Embedding 97M via LocalAI under emulated Lite). Until then the vector path stays optional:
   with no `Embedder` configured nothing here loads (no cache, no resident vectors, no goroutines, no
   embedder call), so the idle cost of the feature is a few empty tables.
2. **When vectors are used, the deterministic method is an exact scan.** No training step, no graph,
   no approximation parameters, no model beyond the embedder the index exists to serve. A search scores
   every authorised vector, so its recall is bounded only by int8 quantisation, and the result is
   reproducible down to ties (`Info.StableTies`). This was tried first and it met the bars (below), so
   an approximate index was not built.

Not benchmarked, with the reason (a candidate that cannot be shipped is not worth measuring):

- **Pure-Go HNSW (`coder/hnsw`).** Does not compile for windows/amd64 or windows/arm64 (verified
  2026-10-02), so it fails the pure-Go-on-every-target requirement; CC0 is outside the licence
  allowlist; per-scope filtering and deletes are unsolved in a graph. A graph also adds RAM on top of
  the vectors it indexes. Kept as the ANN option above the ceiling, behind the same interface.
- **float32 or float16 storage.** float32 is 1,536 bytes a vector (154 MB per 100,000 against 38 MB for
  int8) and the scalar Go scan was within 15% of the int8 speed in the M0-16 scratch measurement, so
  float vectors buy no latency and cost 4x the memory. int8 recall is already 0.976 to 0.990. float16
  originals beside the int8 codes would add 77 MB per 100,000 to allow a later re-quantisation that the
  rebuild-from-chunks path already provides.
- **Upstream Vec1, an external vector database, LocalAI Stores.** Rejected on architecture grounds in
  the ADR (C-only and young; violates §5.1; couples retrieval to one runtime).

## Decision
**The exact int8 flat scan in the core store (candidate A), with the optional resident cache as a
per-profile dial.** It is the smallest candidate that meets the bars: no new dependency, no new
process, and the cache (the only RAM it adds) is optional, sized at about 0.45 KiB per hot vector.

- It meets the 0.95 recall bar everywhere measured (0.976 to 0.990).
- With the 64 MiB cache it meets the 150 ms p95 bar at 100,000 vectors per workspace with a wide
  margin. Without it, it meets the bar up to 25,000 vectors per workspace, and not at 100,000.
- sqlite-vec (B) was built and passes the same contract suite. It is faster than the uncached scan
  (1.5 to 2x) and about 3x slower than the cached scan, ingests 4 to 6x slower, deletes a generation
  10 to 25x slower, and has process-wide side effects. It stays available behind the interface and is
  not linked by default. Its L2 variant fails the recall bar (0.922) and is rejected.
- Rejected: HNSW (not shippable), float storage (4x memory for no speed), anything external.

Supported Lite corpus ceiling (ADR 0011 states it with the evidence): **100,000 active vectors per
workspace and 250,000 per deployment with the default cache; 25,000 per workspace with the cache off.**

## 4 GB profile impact
**Preserves the 4 GB target; it makes nothing harder, and the one memory dial is explicit.**

The index adds no process, no service and no model, and holds nothing resident unless a search asks
for it, so it keeps the 4 GB target possible. It does not make the target harder and it gives the
profile one explicit knob.

- **With the cache off**, the index costs the 31 to 36 MiB of a bare process plus SQLite's bounded
  page caches at any corpus up to 100,000 vectors, and supports 25,000 vectors per workspace within
  the latency bar. This is where the experimental-4g profile starts, and it is the configuration
  `Config.CacheMiB = 0` selects.
- **The one dial** is `cache_mib`: about 0.38 KiB steady (0.45 KiB budgeted) per hot vector. For the
  25,000-vector ceiling that is about 11 MiB, 0.3% of 4 GB, and it takes the streamed p95 from 51 to 57 ms
  to about 11 ms; for the full 100,000 it is 37 MiB, about 1%, and it is what lifts the supported ceiling from
  25,000 to 100,000 vectors per workspace. Whether to spend it is a decision for the profile once the
  full workload's RSS is known (M5), not for this task. A cache that cannot hold the hot set streams
  the overflow at cache-off speed rather than thrashing (admission control), so a too-small value is
  safe.
- **Against B** (sqlite-vec): 13 MiB more resident than A streamed at 100,000 vectors and no dial to
  buy latency back with RAM, plus a fixed 384 dimension and a process-wide extension; it does not help
  the 4 GB profile.
- No model is duplicated or kept resident by the index. The embedder is the shared model of
  `AIRuntimeProvider`, called only from class-5 jobs.
- **Not measured:** the 4 GB profile itself. These are dev-box and emulated 8 GB / 4 CPU numbers; the
  profile's own run is owed to M5 and M2-15.

## Re-evaluation trigger
Reopen this review, and re-run the matrix (`ALIXAI_VECTOR_BENCH=1 go test -run TestBenchMatrix -v
-timeout 90m ./internal/rag/vector/sqlitevec/`), when any of these happens:

- **M2-15 reports recall@10 under 0.95** on a real Granite-embedded corpus (the synthetic figures here
  are 0.976 to 0.990): reconsider the stored format (higher precision, ADR 0011 stored format).
- **A workspace needs more than the ceiling** (100,000 active vectors with the cache, 25,000 without),
  or the Balanced profile is designed: add an ANN or external provider behind the same interface; a
  pure-Go HNSW that builds on Windows and has an allowlisted licence is the first candidate.
- **sqlite-vec changes:** a 1.0 release, a pure-Go port of upstream Vec1, or a batched generation
  delete in the B provider. The overturn criterion (B faster than A at equal recall) already fires for
  the cache-off configuration, so these would make B a real alternative to rerun.
- **The embedding model changes**, in dimension or in kind (the flat provider takes any dimension per
  generation; B's table is fixed at 384).
- **M5 or M2-15 produce certified or 4 GB-profile numbers** that disagree with these emulated ones
  by more than the margins stated in ADR 0011 (2.5 to 3.5x).
- At the latest at the M5 gate, whichever comes first.
