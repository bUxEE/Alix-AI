# Efficiency review — M0-13: live runtime spike, controller and embedding candidates on x86-64 (emulated Lite)

Every feature records this before it counts as done.

All figures are **emulated**: one LocalAI v4.10.0 container capped by cgroup (lite = 8 GiB and 4 CPUs, balanced = 16 GiB and
8 CPUs, no swap) on an i7-10700K host (8 cores, 16 threads, 64 GB) under Docker Desktop, no GPU. They are not a certified
machine (§7.4) and other agents' containers ran on the same host during the session, so latency is indicative. Every number
traces to the raw results of the M0 spike (not published; [the spike report](../evidence/m0-spike/report.md) summarises them); the pass bar was
written before the results ([report](../evidence/m0-spike/report.md)). "RSS" below is the summed resident set of the LocalAI processes (the backend's
memory-mapped weights are file-backed pages and count in it); "docker stats" is the cgroup figure the bench tool records.

## Requirement
The conversational controller maps one short user message to one typed `TaskProposal` (capability id from the application's
catalogue or null, intent, fields) that validates against `schemas/conversation/task-proposal.schema.json`, refuses what the
catalogue does not offer, and cannot be talked into a capability outside the catalogue. Pass bar on the v0 corpus (80 cases,
English and Italian) under the lite profile with a GBNF grammar: schema-valid at least 99%, capability routing at least 90%,
refusals at least 95%, injection resistance 100%, no provider errors, peak memory at most 5.8 GiB (8 GiB cap, minus the 15%
headroom of §7.4, minus 1 GiB for the core and the OS). The embedding model must load under the pinned backend, return 384
finite dimensions and reach mean recall@1 of at least 0.90 on a small English/Italian set, within 0.05 of the Q8_0 file.

## No-model / deterministic option
Measured, not assumed: a keyword router (tokenise, drop stop words, match the catalogue's id, description, field names and enum
values; a tie or no match means "no capability / out_of_scope"; no aliases, no tuning on the corpus), `tests/live/spike/baseline/rules-baseline.mjs`
(its raw result is not published).

| Line of the bar | Keyword router | Bar |
|---|---|---|
| capability routing | 33/54 (61.1%; English 70.4%, Italian 51.9%) | 90% |
| refusal correctness | 12/16 (75.0%) | 95% |
| injection resistance | 14/16 (87.5%) | 100% |
| cost | about 0.17 ms per case in a Node process, no model, no extra memory | |

It does not pass either, and a keyword router with no per-language aliases cannot reach Italian. But it beats Granite 350M on
every line, matches Granite 1B on refusal and injection, and costs nothing, so it stays the floor: the registry's
`degraded_mode: deterministic-routing` (typed forms plus deterministic rules) is what Lite serves until a model passes. A schema
and a GBNF grammar remove invalid shapes but not wrong choices (see Candidates). The cheapest improvement is not a bigger model:
every candidate labels many task cases `help` and out-of-scope requests `help`, because `bench-prompt-v0` never defines `task`,
`help` or `out_of_scope` beyond one clause. A prompt with the intents defined, tested first, costs about ten minutes per model.

## Candidates evaluated
Smallest first. File = Q4_K_M GGUF size. RSS = summed process resident set, peak over the run; docker stats peak in brackets.
Latency = bench request p50 / p95 under the gate run (grammar), prompt about 330 tokens in, 50 to 90 out. Quality = the four
gated lines, schema-valid / routing / refusal / injection (bar: 80/80, 49/54, 16/16, 16/16).

| Candidate | File | Peak RSS (docker stats) | p50 / p95 | Quality | Licence | Verdict |
|---|---|---|---|---|---|---|
| no-model keyword router | 0 | none | 0.17 ms | n/a / 33/54 / 12/16 / 14/16 | n/a | floor, not a pass |
| Granite 4.0 350M | 237 MB | 853 MiB (526) | 2.2 s / 3.0 s | 55/80 / 0/54 / 0/16 / 8/16 | Apache-2.0 | rejected |

What the numbers say, each from the evidence files:

- **Granite 350M** is fast and small and fails everything: it never picks a capability (0/54) and its grammar-constrained output
  breaks `maxProperties` on `fields` in 25 cases (a GBNF grammar cannot express it, so validation after decoding stays mandatory).
- **Qwen3.5-0.8B** routes 52/54 correctly, the best routing of any candidate, and refuses nothing (0/16: it answers out-of-scope
  requests with a capability or `help`). Four of its outputs run to the 256-token cap and are invalid JSON.
- **Granite 1B** is the most balanced Lite candidate and still misses all four lines.
- **Qwen3.5-2B** has perfect shape and perfect injection resistance and misses routing by one case (48 of the 49 needed) and
  refusal by a wide margin (7/16). It is the closest, on the 16 GiB profile only.
- Constraint comparison, same corpus: `json_schema` as the gateway sends it equals "no constraint" for all four models
  (0.8B 65/80 in both, 1B 13/80 in both, 2B 44/80 in both, 350M 0/80 in both): the runtime silently drops it. `json-schema-probe.json`
  isolates the cause on the 0.8B (five requests per variant): the gateway's compact schema 0/5 valid; only `entity_refs` changed to
  `{type: array, items: {type: string}}` 5/5; `items` plus `maxItems: 0` 0/5; a plain `{type: array}` 0/5; `entity_refs` dropped from
  `properties` and `required` 5/5. An array without `items` or with `maxItems: 0` makes the runtime's schema-to-grammar conversion fail
  and the request runs unconstrained. A GBNF grammar works (the gate runs). The TaskProposal therefore needs a grammar, or a schema
  without those shapes, plus validation after decoding in either case.
- **Embedding:** the `modern-bert` architecture loads under the pinned llama-cpp backend. Q4_K_M is not worse than Q8_0 on this
  small set (the set cannot rank two close models) and the vectors agree (mean cosine 0.997), so the smaller file stays the default.

## Decision
- **No controller model qualifies for Lite, so there is no provisional Lite default.** Granite 4.0 1B, the named fallback, also
  fails (schema 74/80, routing 37/54, refusal 12/16, injection 14/16). The rule is explicit: Lite is not certified by
  lowering the bar. The bar was not changed.
- All four controller entries are `rejected` in the registry with their measurements; `default_for` is cleared and the three
  fallbacks to Granite 1B are nulled in the same change. `rejected -> candidate` is the re-evaluation path.
- The Lite behaviour today is the deterministic path (typed forms plus the keyword router as a floor), which already costs nothing.
- The smallest candidate that comes close is Qwen3.5-0.8B on routing and Qwen3.5-2B on shape and injection; larger models
  (3B and above) are **not** evaluated here and are not recommended before the prompt is fixed: the failures are about refusal and
  intent labelling, which `bench-prompt-v0` under-specifies, and a larger model would hide that rather than fix it. Any larger
  candidate must also fit the 5.8 GiB peak line: Granite 1B already uses 2.6 GiB RSS and Qwen3.5-2B 2.7 GiB.
- The embedding model is `qualified-emulated` for LocalAI v4.10.0 (not certified) and stays the default for Lite and Balanced.

## Resource impact
All emulated; lite = 8 GiB / 4 CPU unless stated.

| | 350M | 0.8B | 1B | 2B (balanced) | Embedding Q4_K_M |
|---|---|---|---|---|---|
| model file on disk | 237 MB | 533 MB | 1.02 GB | 1.28 GB | 105 MB |
| RSS peak / median | 853 / 836 MiB | 1700 / 1631 MiB | 2702 / 2583 MiB | 2776 / 2638 MiB | 390 / 386 MiB |
| of which anonymous (peak) | 524 MiB | 1092 MiB | 1626 MiB | 1455 MiB | 189 MiB |
| docker stats peak | 526 MiB | 1033 MiB | 1615 MiB | 1414 MiB | not sampled |
| first request after start (cold) | 7.6 s | 50.4 s | 31.9 s | 27.1 s | 7.3 s |
| decode speed | 39.8 tok/s | 16.8 tok/s | 10.5 tok/s | 9.1 tok/s | n/a |
| time to first token p50 | 0.6 s | 2.5 s | 3.3 s | 3.5 s | n/a |

- Storage: the model files above total 3.2 GB in the bind-mounted data directory, plus 162 MB for the `cpu-llama-cpp` backend. The
  image is about 280 MiB compressed. Q8 embedding adds 115 MB and is not needed.
- Concurrency: one request at a time was measured; `LOCALAI_MAX_ACTIVE_BACKENDS=1` means switching model unloads the resident
  one, so the first request for another model pays the cold load (50 s for the 0.8B on the first load; 9.6 s when the file was
  already in the page cache). The first end-to-end attempt hit exactly that and the gateway's 60 s budget returned a typed 504
  (`logs/e2e-cold-start-timeout.log`): the service needs a warm-up step or a longer first-call budget.
- Prompt processing dominates short answers: about 3 s of every 7 to 10 s is the time to first token for a roughly 330-token
  prompt on 4 CPUs.
- CPU utilisation and power were **not** measured (no sampler for them in this spike); only memory and latency were.
- Constraint cost: grammar, schema and none gave the same latency within noise for the same model (for example 0.8B p50 7.2 s,
  7.1 s, 6.8 s).

## 4 GB profile impact
Not measured under the `4g` cap for any controller. What the data supports:

- The anonymous memory (the part that cannot be dropped) is 524 MiB for 350M, 1.1 GiB for 0.8B, 1.6 GiB for 1B and 1.5 GiB for 2B.
  Those would fit a 4 GiB cap in principle, but the resident set counts memory-mapped weights as well (2.7 GiB for 1B), and under a
  4 GiB cap the page cache holding the weights competes with the core, SQLite and the embedding worker. Whether that thrashes is
  not measured; §7.4 asks for no repeated eviction and reload.
- The embedding model alone adds 390 MiB RSS (189 MiB anonymous); LocalAI keeps one backend resident, so a controller and the
  embedding model are not resident together: each switch is a reload (about 7 s for the embedder).
- Net: **preserves** the 4 GB direction for now only because the answer on Lite is the deterministic path, which adds nothing.
  Any controller that qualifies later makes it harder by 0.8 to 2.7 GiB RSS. The one real out-of-memory probe (`m0-oom`, a 131072-token
  window under the 4 GiB cap) is in `error-mapping-4g.json` where it was run.

## Re-evaluation trigger
- Immediately: a `bench-prompt-v1` (outside this task's scope, `tools/bench`) that defines `task`, `help`, `cancel` and
  `out_of_scope` and reaches the intent fields the corpus checks; re-run the four candidates (about ten minutes each) before any
  larger model is considered.
- A new Qwen or Granite release in the 0.5B to 2B range, or a different quantisation of the same models.
- A LocalAI bump (the runtime version is part of every qualification: `allowed_runtime_versions` lists only v4.10.0).
- The first M1 prompt builder (`internal/dialogue`), which replaces the bench prompt.
- Real target hardware (an 8 GB x86-64 and an ARM64 machine): nothing here is certified.
- Review date: 2026-12-02, or earlier on any of the above.
