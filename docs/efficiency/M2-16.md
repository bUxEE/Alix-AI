# Efficiency review — M2-16: RAG composition, read-by-reference and the recheck hint

Every feature records this before it counts as done. The code is
`internal/cli/cmd_rag.go` (the composition), `internal/rag/index/hits.go` and `recheck.go` (the two
index changes) and `internal/rag/query/stopwords.go`. The figures are **dev box** figures (Windows 11,
Intel i7-10700K, Go 1.27, `CGO_ENABLED=0`, modernc.org/sqlite, a shared machine with antivirus), neither
emulated nor certified. The Recheck and Hits figures come from `go test -run TestBenchRecheck` in
`internal/rag/index` (env-gated, `ALIXAI_RECHECK_BENCH=1000,10000,50000`); the process figures from
`alixai serve` binaries built with `-ldflags="-s -w" -trimpath`, started by a script that kept each PID
it started and read the working set of that PID (PowerShell `Process.WorkingSet64` and
`PrivateMemorySize64`, not Go's `runtime.MemStats`).

## Requirement
- **Recheck (the final authorisation and version recheck).** Every query ends with
  `index.Recheck` of the chunks it is about to cite. M2-09 measured it at 16.1 ms per query at 10k chunks
  in one scope and 240 ms of a 423 ms query at 50k, because SQLite, which has no statistics here, reads each
  chunk through the scope index `ragindex_chunk_doc` (three equalities: it looks the most selective) and
  walks the whole workspace to find one row. It must be a lookup, and it must stay one: a test has to fail
  if the plan scans.
- **Read by reference.** The vector index returns chunk, generation and source ids and no text, so the hybrid
  pipeline needs `index.Hits(ctx, scope, refs, includeHidden)` to add a candidate only the vector stage found
  (the `query.HitReader` contract). It must return exactly what `Search` returns for the chunk, only under the
  caller's scope, and a chunk of another scope, a hidden one, a deleted one and one that never existed must be
  indistinguishable (no hit, no error).
- **Composition (§3 rules 12 and 13, §17.2, §18).** Ingest and query run inside `alixai serve` with: the
  disk-pressure pause installed on the queue before it exists; ingestion yielding to every interactive class
  (jobs `interactive_up_to_class` = 4); the parser worker probed at start and its readiness reaching `/readyz`;
  a source readable only through a deterministic catalog (active package, registration, scope) that fails
  closed; operator actions (confirm a held mass deletion, delete a tenant) authorised by verified identity and
  never by a role a token or a package asserts, and never by the model. A deployment that never ingests must
  not pay for it: no model, no process started, no scan, no connection at start.
- **One list of stop words**, exported by the query package for whoever must agree with it, not copied.

## No-model / deterministic option
Everything here is deterministic; there is no model in any part of this task, so this is the option taken.

- Recheck and Hits are SQL. The only candidate for a "smarter" Recheck is a cache of verdicts, which this
  review rejects: a verdict cached across the revocation of a source or the replacement of a document is the
  exact failure the recheck exists to prevent (SEC-028), and the lookup it would save is now 0.1 ms.
- The catalog, the operator authority and the job authority are tables and comparisons: a registration, the
  active package's content hash, the verified scope's application and principal ids. Nothing is inferred.
- The embedder is the one optional model, and it is not new: it is wired only when an embedder role is registered
  **and** `rag.embedding.model` and `component_version` are set. Without one, ingestion is text-only and queries
  are full-text labelled `reduced_semantic_recall` (§18). Today `serve` registers no embedder role, so the
  deployed composition is the no-model one.

## Decision
- **Recheck uses `INDEXED BY ragindex_chunk_live`.** 1.7 to 1.9 s down to 5 to 6 ms for 50 refs at 50k chunks
  (about 300 times), 200 ms down to 4 ms at 10k (about 50 times), and flat across 1k, 10k and 50k, where the
  unhinted statement is linear. The per-query cost the brief quotes (16.1 ms to 0.5 ms at 10k; 240 ms of 423 ms at
  50k) is this per-ref cost times the handful of refs of a query: 4 refs at 4.1 ms is 16 ms. The hint is also a
  guard: if the index is dropped or its predicate stops matching, the statement fails with "no query solution"
  instead of silently scanning. `TestRecheckUsesTheLiveChunkIndex` reads the plan of the statement Recheck really
  ran (through the trace seam, which Recheck now reports to) and fails on a scan, on the scope index, or on the
  live index with the wrong columns; `TestRecheckPlanCheckerRejectsScans` proves the checker rejects each of those,
  and the test was run against the statement with the hint taken out and failed before it was kept.
- **`index.Hits` is two steps over the statements `Search` already trusts:** each ref to its row through the live
  index under the scope predicate, then `readHits` (the whole visibility predicate repeated, and the in-Go check
  that refuses the whole result if a row of another scope appears). One shape of Hit for both paths, so a
  vector-only candidate cannot differ from a full-text one.
- **The composition is built from what exists and costs +2.6 MiB of working set, +1.9 MiB private and 1.3 MB of
  binary when idle.** What it adds when nothing is registered: a job pool (one goroutine, one wake-up a second
  and one read-only query per class that has handlers, so two a second), a re-audit ticker (one wake-up every
  30 s, no query unless a source is registered), a parser readiness probe goroutine that starts no process when
  the worker is not installed, and the in-memory structures of the index, the chunker and the query pipeline. The
  parser runner is built lazily, so a deployment with no worker installed starts, and a worker installed later is
  picked up by the probe ingest repeats once a minute. No vector index is built without an embedder.
- **The catalog reuses a source's availability label for 5 s** (`ragStatusTTL`): takes the catalog out of a warm query
  (8.1 to 4.1 ms at 500 documents, 19.7 to 11.0 ms at 2,000; table above). It never reuses an authorisation.
- **Rejected:** a separate always-on ingestion process (a second resident Go runtime for a service that is idle
  most of the day); starting the parser worker at serve start (70 to 112 ms a start on Windows, 26.5 s the first
  time under Avast, for nothing if no source is ever registered: the probe runs in the background and never blocks
  `serve`); failing `/readyz` whenever the worker is missing (a deployment that never ingests would be unready);
  persisting the source registry in a new SQLite module from this file (a migration and a public store belong to a
  task with that scope; see the report).

## Resource impact
- **RAM.** Idle `serve`: +2.6 MiB working set, +1.9 MiB private (dev box, five starts each, an external reading of
  the PID the script started). Not included, and each is separate: one disposable parser worker process per
  document under ingestion (ADR 0014: 37 ms on Linux, 70 to 112 ms on Windows, memory limit 512 MiB by default,
  `rag_ingest.parser.max_concurrent` defaults to 1, so at most one at a time); the resident vector cache (a budget
  of `rag_vector.cache_mib`, default 64 MiB, loaded only when an embedder is configured and a generation is
  searched; 0 turns it off); the chunker and index working set while a document is indexed (M2-08, M2-06).
- **CPU.** Idle: one 15.6 ms clock tick in 20 s for the process, against none for the baseline, which is the
  pool's second-by-second poll and is about 0.08 % of one core at the measurement's resolution. Under work it is
  the pipeline's: Recheck and Hits are SQL lookups of 0.1 to 0.5 ms a chunk.
- **Storage.** None added by this task: no migration, no table. The registry is in memory.
- **Latency.** Recheck at 50k chunks in one scope: from 33 to 37 ms a chunk to 0.1 ms, which is 240 ms of M2-09's
  423 ms query. Hits: 0.08 to 0.5 ms a chunk, only for vector-only candidates. The catalog, with the label reused:
  under 0.01 ms warm and one status read (1.5 ms at 500 documents, 4 ms at 2,000) every 5 s per source. The
  composition adds no other per-query work.
- **Concurrency.** Ingestion yields to classes 1 to 4 (`interactive_up_to_class` = 4, raised to 4 when the
  configured value is lower, asserted by `TestRAGServeWiringOrder`), and pauses on disk pressure: the pause is the
  queue's own `DequeuePolicy`, so a paused job is not leased and spends no attempt. The disk floor is
  `rag.disk_floor_bytes` (default 1 GiB of free space on the data directory's volume; a volume that cannot be
  measured is pressure).
- **Power.** The idle wake-ups above are the whole of it; no timer shorter than one second runs.
- **Binary.** +1.30 MB (20.83 to 22.13 MB, 6.2 %), the ingest, query, vector, parser-runner and filesystem-provider
  packages that `serve` now links.

## 4 GB profile impact
**Preserves it.** An idle process costs 2.6 MiB more and nothing is loaded for an unused feature (rule 12): no
model, no vector index, no parser process, no scan until a source is registered. Two things in the profile are
worth knowing and neither is new: (1) ingestion's peak is the parser worker's memory limit (512 MiB by default, one
at a time), the largest single allocation of the RAG path, which `rag_ingest.parser` can lower; (2) the default
disk floor of 1 GiB is chosen for the Lite profile and should be lowered with `rag.disk_floor_bytes` on a small
volume, or ingestion will stay paused. `experimental-4g` starts at `rag_vector.cache_mib: 0` (the `rag_vector` section's own guidance, ADR 0011).
Recheck's fix helps the profile: it removes the one query cost that grew with the size of a workspace, and a
4 GB host that holds a 50k-chunk workspace no longer spends 240 ms of a 423 ms query on it.

## Re-evaluation trigger
- M3-17 (resource governor) lands its own disk-pressure detector and admission control: replace the interim
  `ragDiskPressure` (free space of the data directory against one floor) with it, and re-measure the idle cost.
- A SQLite upgrade (modernc.org/sqlite): the test logs whether the planner now picks the live index unaided; if so
  the hint is redundant but harmless, and the plan test still guards it.
- The source registry becomes durable and the RAG routes (M2-11) call it: re-measure the idle and registered
  costs, and the re-audit ticker, which then reads real packages from disk.
- An embedder role is registered by `serve` (M2-15): re-measure with the vector cache and the embedding queue
  on, labelled emulated if taken in a resource-limited container.
- A corpus beyond 50k chunks in one scope, or a query that rechecks far more than 50 chunks at once
  (`MaxRecheckRefs` is 1,000): the per-ref cost is flat, but the per-query total is not.
