# Efficiency review — M0-06: durable SQLite-backed job queue with priority classes

Every feature records this before it counts as done.

All numbers below were measured on the same Windows 11 dev box as the M0-05 review (16 logical CPUs,
NVMe) with Go 1.27, `CGO_ENABLED=0`, `modernc.org/sqlite` v1.60.1, and are labelled **dev box**. They
are not from a resource-limited container, so they are neither **emulated** nor **certified**. The
measurement is kept as a test so it can be repeated on any host:

```
ALIXAI_PROBE_JOBS=10000 go test -run TestJobsFootprint -v ./internal/jobs/     # about 30 s, the figures below
go test -run TestQueryPlansUseTheIndexes -v ./internal/jobs/                   # the query plans
```

`TestJobsFootprint` re-executes the test binary as a child process (`internal/jobs/probe_test.go`), so
the memory figures are the OS's view of a process that only ran the queue (about 9.8 MiB resident
before anything opens), not the accumulated state of a test run. The default run uses 3 000 jobs
(about 10 s) and enforces a 128 MiB ceiling on growth over the bare process. This host's timer ticks
at 1 ms, which makes individual sub-millisecond latencies useless, so every latency below is a mean
over a loop of 200 to 10 000 operations, never a percentile. Ranges are over two to four runs.

## Requirement
A durable, bounded queue for the work §3 rule 13 names (parsing, OCR, indexing, embeddings, bulk
synchronisation, maintenance) that replaces Redis in the minimum profile (§6, ADR 0007):

- jobs survive a restart and a worker crash (a lease that is not heartbeated expires and the job
  returns to `pending`), are idempotent to enqueue, retry with exponential backoff and jitter up to a
  per-type attempt limit, end `failed` with an error code, honour deadlines (`timeout`) and
  cancellation (a running job's context is cancelled);
- six priority classes (§17.1), each with a worker limit and a bounded depth, and lower classes yield:
  while a class 1 or 2 job is waiting, class 5 and 6 workers lease nothing (§3 rule 12);
- every job keeps its initiating scope and a `ScopeChecker` re-validates it before the run; a revoked or
  expired scope fails the job with `permission_denied` unless a declared service identity is
  authorised (§10.2, §3 rule 14);
- hooks M5-06 needs and cannot add itself (ADR 0018): an `EnqueueGuard` that can reject with
  `rate_limited` or `resource_exhausted`, and a pluggable intra-class dequeue ordering;
- observable counts per class and state for the operations API.

Footprint budget: no resident service, no always-on thread beyond one wake-up per poll interval, memory
bounded by configuration (§3 rules 12, 16, 17).

## No-model / deterministic option
There is no model in this feature. It is entirely deterministic code, so this section is about the
smallest *infrastructure* that does the job, and the safety-relevant decisions are all deterministic
rules: the class of a job comes from its registered type (a producer cannot promote its own work), the
scope check and the service-identity check are hooks answered by identity state (a job that merely
names a service identity gets nothing), and every failure path ends in a typed state, never a
success-looking one.

- **In-memory queue** (slice or channel behind a mutex). Measured in a throwaway program (not
  committed): 88 ns to enqueue and 15 ns to lease. Rejected on the requirement, not on speed: a
  restart loses every queued job and nothing can be inspected or retried durably.
- **Redis with a job library, or an embedded broker (NATS JetStream and similar).** Rejected in ADR 0007
  and §6 for the minimum profile: a resident service and a second persistence and backup story. Not
  measured: there is no Redis or broker on this box, and the argument is structural (an extra process
  against rule 17), not a figure.
- **SQLite queue tables in the existing core store (chosen).** One more table in a database that is
  already open, no extra process, transactional with the data it works on. The cost controls are
  deterministic decisions, measured below: work is leased only when a class has a free worker, so
  concurrency never exceeds the configured limit; an idle poll is read-only and takes no write lock;
  every hot statement runs from a partial index (pinned by `TestQueryPlansUseTheIndexes`); depth,
  payload and retention are all bounded.

## Decision
SQLite tables in the core store, module `jobs`, one table (`jobs`) and six partial indexes, behind the
`Queue` API (enqueue, lease, heartbeat, complete, fail, release, cancel, reap, prune, status), with a
`Pool` that runs handlers. Defaults, all in the registered `jobs` config section (`ALIXAI_JOBS_*`):

| Setting | Default | Why |
|---|---|---|
| Workers per class 1, 2, 3, 4, 5, 6 | 2, 2, 2, 2, 1, 1 | Workers are goroutines started per leased job, not idle threads, so the limit costs nothing until used; one worker each for the two background classes caps parsing and OCR concurrency at two jobs in the Lite profile |
| Depth per class | 256, 256, 256, 512, 5 000, 1 000 | Finite for every class (an unbounded value cannot be configured). Class 5 is large because an ingestion burst enqueues one job per document; 5 000 jobs cost about 3 MiB (595 bytes each) |
| Poll interval | 1 s | An enqueue in this process wakes the pool at once (tested with a one-minute interval); the poll only finds work that arrived another way (another process, an elapsed backoff, an expired lease). 1 s costs 0.023 % of one core (below) |
| Lease TTL, heartbeat | 30 s, every 10 s | A crashed worker's job is back in about 30 s plus the maintenance interval (TTL / 4); a heartbeat is one tiny write per running job per 10 s |
| Max attempts, backoff | 5, 2 s doubling to 5 min, jittered into [d/2, d] | Spreads retries so a recovering dependency is not hit in step. A lease that expires on the last attempt fails with `uncertain_outcome`, so a job that kills its worker cannot loop forever |
| Payload cap | 64 KiB | A payload is a reference to work, not the data; bounds row size and the memory of a leased batch |
| Finished-job retention | 7 days | Keeps failures inspectable and idempotency keys alive; `Prune` deletes at most 1 000 rows per transaction (4.8 to 5.1 ms) so the writer is never held long |

Choices the plan left open, recorded for the ADR owner: class depth counts *waiting* (`pending`) jobs
only, since running jobs are already bounded by the worker limits; an unknown handler error (a plain
error) is **not** retried, only a retryable `contracts` code is, so a non-idempotent handler is never
re-run by accident; a job that declares a service identity the `ServiceAuthorizer` does not accept is
denied, never run under the principal's scope instead; `NewPool` refuses to start without a
`ScopeChecker`; the policy orders only inside a class, so no policy can reorder priority classes.

Larger candidates rejected and why: Redis or a broker (a resident service, §6); counters or covering
columns for speed (measured above, not worth their write cost or second source of truth at these
volumes); a push-only design with no poll (a crash or another process's enqueue would then go unnoticed).

## Resource impact
All **dev box**, 10 000 queued jobs of 189-byte payload and about 250 bytes of stored scope unless noted.

- **CPU, idle.** One `Pool.Poll` with a handler for every class is 221 to 230 us, 192 allocations,
  7.2 KB, about eight read-only statements through the reader pool; at the 1 s default that is 0.023 %
  of one core. It takes no write lock and writes nothing. `Reap` when nothing is due is one read-only
  statement (under the 1 ms timer tick). Wake-ups: one timer per second per running Pool.
- **CPU, busy.** The writer is the limit. One job per transaction: lease then complete is 1 323 to 1 335
  jobs/s at depth 10 000 (1 642 to 1 645 at depth 3 000). Through the Pool with a no-op handler, end to
  end including the cancel-flag read and heartbeat set-up: 724 to 772 jobs/s with one class-5 worker
  and 1 650 to 1 700 jobs/s with eight class-4 workers, which batch their leases. Enqueue is 1 390 to
  1 416 jobs/s overall at 10 000 (2 366 to 2 391 at 3 000). Real handlers (parse, OCR, embed) are expected to take tens of
  milliseconds or more (not measured here, the parsers do not exist yet), so the queue should not be
  their bottleneck; ADR 0007's rule stands: batch many small
  items into fewer jobs.
- **RAM, steady.** Opening the store, the queue and a pool with six handlers adds 2.7 to 2.9 MiB resident
  (9.8 to about 12.6 MiB); the Go heap in use is 1.3 to 1.5 MiB. The process has 5 goroutines after
  opening (2 before), all from the store's connection pools: `NewQueue` and `NewPool` start none, and
  `Run` adds one. Jobs hold no memory while they wait: only leased jobs are read
  into memory.
- **RAM, loaded.** 10 000 queued jobs raised the working set to 35.3 to 36.0 MiB (+23 MiB over idle);
  with 3 000 queued it was 26.8 to 27.0 MiB. That is the store's page cache and allocator filling to
  the 16 MB budget M0-05 measured, not per-job memory. Peak over the whole run, every probe included,
  was 40.1 to 40.7 MiB.
- **Storage.** 595 bytes per job (5.68 MiB for 10 000, of which the payload is 189 bytes, the stored scope
  about 250 and the rest columns and six partial-index entries), 606 to 613 bytes in the 3 000-job runs.
  The WAL stayed at 3.95 MiB, under the 64 MiB `journal_size_limit`. At the default depths a full queue
  is 7 280 jobs, about 4.3 MiB; a week of retention at 10 000 finished jobs a day is about 40 MiB.
- **Latency.** Enqueue 0.36 to 0.39 ms for the first 1 000 jobs, 0.99 to 1.0 ms at depth 9 000 to
  10 000 (the depth count scans the ready index). Lease 0.41 to 0.52 ms single and 0.18 to 0.27 ms per
  job in batches of 16. Complete 0.19 to 0.25 ms. `Status` 0.8 to 3.7 ms at 3 000 to 10 000 rows
  (operations call, not on a timer). A custom dequeue policy raises lease cost to 1.7 to 2.3 ms with one
  tenant and 1 500 jobs queued and 3.0 to 3.3 ms with 500 tenants of 3 jobs each (O(queued), against
  0.5 ms for the default), so install one for fairness, not by default.
- **Concurrency.** Per-class worker limits hold: `TestWorkerConcurrencyLimitPerClass` observes exactly
  the configured maximum (2 and 1) and never more, with the classes isolated from one another.
  Concurrent leasing from six goroutines never hands one job to two workers
  (`TestConcurrentLeasesNeverShareAJob`). `-race` is not runnable on this host (no cgo); it runs in Linux
  CI.
- **Yielding.** Background work is held while an interactive job waits (`TestBackgroundYieldsToInteractive`,
  `TestPoolBackgroundYieldsToInteractiveJobs`); the cost is one extra indexed probe per background-class
  lease.
- **Power.** Not measured. The only recurring activity is the 1 s poll above.

## 4 GB profile impact
**Preserves** the 4 GB target. The queue is a library inside the existing process: no second service
(Redis would be one), about 3 MiB resident at idle, and everything it adds under load is the store's
configured page-cache budget, which the Small store profile already shrinks (M0-05: +19 MiB peak). The
knobs that matter at 4 GB are all configuration: worker counts (two background workers cap concurrent
parsing and OCR), class depths, retention (disk, not memory), and the poll interval. Nothing here loads
a model or grows with context. What could make it harder was measured and kept off the default path:
the dequeue policy's O(queued) cost applies only when M5-06 installs one, and the per-enqueue depth count
adds 0.3 ms at the largest default depth, not memory. One watch item for M3-17: background leasing is
blocked only by *waiting* interactive jobs, so a class 1 or 2 job with no worker anywhere would hold
back class 5 and 6 (a deployment error, but a visible one: `Status.OldestReadyAgeMs`).

## Re-evaluation trigger
- M2-08 ingestion benchmarks: if one enqueue per document (about 1 400 a second) or the 0.7 to 0.8 thousand
  jobs a second a single class-5 worker sustains is the bottleneck rather than the parsers, add a batch
  enqueue (one transaction for many jobs) and revisit the worker default.
- Any class depth raised above about 50 000: replace the per-enqueue `count(*)` with trigger-maintained
  counters.
- M5-06 installing a fair-dequeue policy: re-measure lease latency at the real tenant counts; the tenant
  columns in the ready index (measured: 25 % faster policy leases, +7 bytes a job) are the first lever.
- M3-17 soak and noisy-neighbour runs: if the single writer shows up in interactive p95 while a class 5
  burst runs, lower the class-5 worker default or batch its completions.
- The first 4 GB emulated run (`experimental-4g`): re-measure idle and loaded RSS inside the container
  and relabel these figures **emulated**.
- A `modernc.org/sqlite` or SQLite upgrade: rerun `TestJobsFootprint` and `TestQueryPlansUseTheIndexes`
  (a partial index is only used when a query repeats its WHERE terms literally, so a planner change is
  caught there).
