# Efficiency review — M2-04: sandboxed parsing workers (finalises ADR 0014)

Every feature records this before it counts as done.

All numbers were measured on the project's Windows 11 dev box (16 logical CPUs, NVMe, Avast active,
Go 1.27, `CGO_ENABLED=0`) and, for Linux, in an alpine container on Docker Desktop's WSL2 VM on the same
machine (Docker 29.7.2, kernel 6.18.33.2, 16 CPUs visible). Labels: **dev box** is the Windows run;
**dev box, Linux container** is the Linux run with no limits; **emulated 4 GB profile** is the Linux
container run with `--memory 4g --cpus 4`, which is neither the certified 4 GB profile nor a
measurement of one. Nothing here ran on a Linux or macOS host of its own, on arm64, or on a machine
with fewer than 16 CPUs.

The measurement is a test, so it can be repeated on any host. A plain `go test` runs only a quick
version (one 100 KiB document per format, as a smoke test of every parser through a real worker and of the
memory ceiling); the measurement is switched on with `ALIXAI_PROBE_PARSE`. The tables below are from the
second command; the first takes about 40 s on this Windows host:

```
ALIXAI_PROBE_PARSE=full go test -run TestParseFootprint -v ./internal/rag/parse/
ALIXAI_PROBE_PARSE=large,reps=5 go test -run TestParseFootprint -v ./internal/rag/parse/
```

`TestParseFootprint` starts the production worker as a real process. Peak memory is the host's view of
that process: on Windows the Job Object's peak committed bytes (what the memory limit counts) and the
process's peak working set; on Linux `VmHWM` of `/proc/<pid>/status` (the kernel's high-water mark for
the worker alone; `rusage` is not used because on Linux it starts at the host's own size, see ADR 0014).
Each row is the median of five runs for times and the largest of five for memory. The timer on this
Windows host ticks at about 1 ms, so "1 ms" means "1 ms or less".

**How far to trust the numbers.** The same test run twice on this machine, an hour apart, differed by up
to 2 times in time (the 13.1 MiB PDF parsed in 1.49 s and in 0.80 s on Windows; start to a verified
sandbox took 95 to 112 ms and then 76 ms) and by up to 15 % in memory (143 and 152 MiB committed for the
same PDF). The tables are the second, quieter run; where the first run matters its range is given in the
text. Read times as plus or minus a factor of 2, memory as plus or minus 15 %, and do not read a
difference smaller than that between two cells as real.

## Requirement
Turn an untrusted file (txt, md, html, csv, pdf, docx) into text, structure and a hidden-text flag that
maps onto `chunk.Document`, without letting a hostile file harm the service (§12.6, §16.2, §16.4):

- parse out of process, one disposable process per document, with mandatory wall-time, memory, CPU and
  output limits on every platform and best-effort OS confinement on top, failing closed when a mandatory
  limit cannot be installed (ADR 0014);
- reject oversized input and output, archive and PDF-stream bombs (ratio, entry count, expanded size,
  nesting) and path-bearing archive entry names; never truncate quietly;
- flag hidden text as its own `Hidden` block, never as an unflagged gap (SEC-012);
- record the parser version with every result and survive a crashing, hanging or memory-hungry document
  as one failed document (SEC-013, SEC-014, SEC-016);
- keep OCR off by default (§7.5: specialist workers load only for bounded jobs);
- footprint: nothing resident while idle, bounded memory while parsing, one parse at a time by default
  (§3 rules 12, 13, 16, 17).

## No-model / deterministic option
There is no model in this feature; every decision is deterministic code, and that is the point: the
parsers are pure Go with no dependency on a native library, a model, a JVM or a service, and the sandbox
decisions (which limits, which level, whether a result is accepted) are made by the host from
deterministic checks, never on the worker's say-so (the worker's confinement report is re-checked, its
result re-validated against its own text).

What was tried against the requirement, smallest first:

- **Existing library in the process.** Rejected on the requirement, not on speed: a Go out-of-memory or
  stack overflow in a parser ends the whole service and runs with its database and keys (ADR 0014,
  option B). Not measured.
- **Own pure-Go parsers behind a disposable process (chosen).** The hidden-text flag needs the graphics
  state at each text operator (fill colour, render mode, font size, clipping, optional content) and the
  CSS, run and style rules of HTML and DOCX; owning the parsers also lets every loop carry a budget.
  I did not benchmark third-party Go PDF or DOCX libraries in this task; the choice rests on that
  requirement and on the hostile-input suite, not on a comparison.
- **Native converters (poppler, Tika, LibreOffice) as workers.** Not measured. They are native code or a
  JVM, which the plan's pure-Go, 4 GB-compatible direction rules out for built-in formats and which would
  need L2 or a container to run at all (ADR 0014, optional adapters).
- **OCR.** Off. No engine ships, so there is nothing to measure: an OCR engine plus model is the opposite
  of the smallest option (an engine and a model resident, and seconds per page; those two figures are the
  usual shape of OCR, not measured here). The hook is the `NeedsOCR` page list in a result. A document
  with no text layer fails `needs_ocr`; `ocr.enabled: true` is refused by `Config.Validate` so that a
  switch cannot silently do nothing.

## Candidates evaluated
Smallest first. "Parse" is the time inside the worker; "end to end" is what the caller waits (process
start and sandbox verification included, process exit not). Figures are for the 1 MiB class of document
(the PDF is 1.6 MiB, the DOCX 322 KiB), Windows then Linux, from the tables below and, for the ranges, the
first run too.

| Candidate | Size | Peak memory | Latency | Quality | Licence | Verdict |
|---|---|---|---|---|---|---|
| In-process parse | no process | inside the service | parse time only | no isolation: a fatal error ends the service | in-repo | rejected on the requirement, not measured |
| **Native pure-Go worker, a process per document (chosen)** | 5.8 MiB executable, 3.9 MiB stripped; nothing resident when idle | Windows 51 to 62 MiB commit (14 to 26 MiB working set); Linux 10 to 22 MiB resident | end to end 86 to 161 ms on Windows, 62 to 197 ms on Linux; parse 7 to 95 ms on Windows, 10 to 155 ms on Linux | 8 required tests, 87 format tests and subtests, 8.7 M fuzz inputs | in-repo | **chosen** |

## Decision
The native pure-Go worker, one disposable process per document, `GOMAXPROCS=1`, default budget 512 MiB,
60 s wall limit, 16 MiB output cap and one concurrent parse (`parse.DefaultConfig`). The pooled and
`wazero` variants are rejected for the reasons in the table and in ADR 0014. Throughput and memory do not
need a smaller candidate: no format needed more than 152 MiB for an 8 MiB result, a third of the 512 MiB
budget, so the budget is a safety margin and not a working need.

Process start is the one cost worth acting on, and most of it is outside the parser: on Windows it is the
operating system's and the antivirus's (back to back, an empty Go program takes 39 to 42 ms to start and
exit, the 5.8 MiB worker 63 to 65 ms and the same worker built with `-ldflags="-s -w" -trimpath` 52 to
56 ms). Shipping the worker stripped and probing it once at service start are recorded in ADR 0014 as
packaging concerns, outside this package.

## Resource impact

### Idle and start
- **Idle:** no process exists between documents; nothing is resident, no thread, no timer. The `Runner`
  holds one empty owner-only temporary directory (the workers' working directory).
- **An idle worker** (started, confined, handshake verified, nothing parsed): Linux 4.1 to 4.6 MiB
  resident; Windows 44.8 MiB committed, 7.3 MiB working set. The Windows commit figure is the Go
  runtime's own reservation and is why `Config.Validate` refuses a budget under 64 MiB.
- **Start to a verified sandbox** (median of 3 to 7 starts per run): Windows 76 ms in the second run
  (70 to 84 ms) and 95 to 112 ms in three earlier runs (86 ms minimum, one 312 ms outlier); Linux 37 ms
  (35 to 41 ms) and 37.5 ms earlier (32 to 57 ms); emulated 4 GB profile 40 ms (36 to 41 ms) and 63 ms
  earlier (58 to 77 ms). Why the earlier runs were slower was not established (other load on the machine and antivirus activity are the candidates).
  Bare start-and-exit of the executable with nothing else, back to back: Windows worker 63 to 65 ms,
  stripped worker 52 to 56 ms, empty Go program 39 to 42 ms; in the earlier, busier period 100 ms,
  54 to 70 ms, 46 ms and 24 ms for `whoami.exe`. Linux worker 36 to 43 ms. The first start of a
  freshly written executable on Windows took 26.3 s and 26.5 s (two executables) while Avast scanned
  it. That is why `StartupTimeout` is separate from the wall limit; the 30 s default clears it by under
  4 s, so a Windows deployment should exclude the worker from on-access scanning or probe it once at
  start-up (`Runner.Probe`).
- **A process per document against one worker for many** (30 documents of 4 KiB; the second run, with
  the range over all runs in brackets):

  | Environment | A process each | Per document | One worker | Per document |
  |---|---:|---:|---:|---:|
  | dev box (Windows) | 2.11 s (2.1 to 4.2 s) | 70 ms (70 to 140 ms) | 4 ms | 0.14 ms (0.14 to 0.47 ms) |
  | dev box, Linux container | 1.35 s (1.3 to 1.7 s) | 45 ms (45 to 56 ms) | 8 ms | 0.28 ms (0.28 to 0.30 ms) |
  | emulated 4 GB profile | 1.21 s (1.2 to 5.3 s) | 40 ms (40 to 177 ms) | 9 ms | 0.31 ms (0.31 to 0.43 ms) |

  Process start and teardown are over 99 % of a small document's cost. For ingest of many small files
  that is the cost to watch; the lever is batching documents of one scope into fewer worker lifetimes
  (a change confined to `Runner`, ADR 0014 overturn criteria), not weakening the isolation.

**Emulated 4 GB profile** (`--memory 4g --cpus 4`) gave the same table within noise: every peak within
1 to 19 MiB of the unconstrained run (the 13.1 MiB PDF at 123 MiB against 104 MiB is the largest gap),
times within 30 % in both directions (the 8 MiB HTML parsed in 209 ms against 276 ms; the 2.5 MiB DOCX in
320 ms against 288 ms), start 40 ms against 37 ms. The full table is in the test's output; no conclusion is
drawn beyond "four CPUs and 4 GB did not change what the worker needs".

Reading the tables:

- **Throughput by format**, in order: txt and md (60 to 180 MiB/s) → html and csv (18 to 44 MiB/s) →
  pdf and docx (5 to 18 MiB/s). PDF text extraction of a 13 MiB, 3 292-page file took 0.8 to 1.5 s.
  Nothing is parallel (`GOMAXPROCS=1`): a parse uses one core for its duration.
- **Host and transfer** is small for documents under 1 MiB (1 to 27 ms) and comparable to the parse for
  8 MiB of plain text, Markdown or CSV (65 to 284 ms): the result carries one block span per paragraph or
  CSV row as JSON (31 035 blocks for the 8 MiB Markdown), and the host checks every span.
- **Memory** is about 5 MiB resident plus 4 to 15 times the text produced (txt 35 MiB for 8 MiB of text,
  md 40, docx 47 for 6.9, html 57 for 7.3, csv 69 for 9.5, pdf 104 to 123 MiB for 8.0). The output cap
  (16 MiB by default) bounds it: extrapolating the PDF ratio puts the worst case at about 250 MiB, half
  the 512 MiB budget. That extrapolation was not measured. The host's own memory (the service holding the
  document, the result and its block list) was not measured separately.

### Limits behaving (the cost of a refusal)
Hostile inputs were refused without a process outliving the call and without the worker's memory
approaching its budget:

- a high-ratio zip (2 MiB of XML inflating 1000:1), 75 MiB of bookmark parts over the total, an entry
  flood of 3 000, nested archives, a header that lies about size, a wrong checksum, overlapping entries
  and four path-bearing names (`..`, absolute, backslash, drive): each refused as `archive_bomb` or
  `malformed` in 0.1 to 2.3 s on Windows with the process start included, the worker's peak under half
  of its 512 MiB budget (`TestZipBombRejected`);
- a PDF content stream of 160 MiB of operators: `archive_bomb` (`TestZipBombRejected/pdf_stream_bomb`);
- hung, spinning, crashing and memory-hungry fixtures each cost exactly one process and one typed error,
  and the runner then parsed the next document (`TestParserTimeoutKilled`, `TestParserCrashIsolated`,
  `TestParserMemoryLimitKilled`);
- `FuzzParse` over all six parsers (16 fuzz workers) found one panic in its first six seconds, in the PDF operand
  reader (fixed and kept as a regression seed), then ran clean for 3 and for 7 minutes, the longer
  run covering 8.7 million inputs. The fuzz engine's own throughput fell to zero for stretches of tens of seconds, which is not
  explained by a slow input: all 1 136 inputs in the saved corpus parse in under 1 ms each. The cause was
  not established (the engine's minimisation and the antivirus on the fuzz cache are the candidates).

### Storage
Nothing is persisted by the parser. The worker executable is 5.8 MiB (default build) and 3.9 MiB with
`-ldflags="-s -w" -trimpath` on both Windows and Linux; the `wasip1` build tried and rejected was 5.1 MiB.
The only file the host makes is the empty working directory (owner-only, removed on `Close`).

### CPU, concurrency, power
- **CPU:** one core while a parse runs (`GOMAXPROCS=1`), nothing when idle. A process start costs about
  40 ms on Linux and 40 to 110 ms on Windows, including the antivirus's scan.
- **Concurrency:** `MaxConcurrent` defaults to 1 and is a semaphore in the `Runner`; the job class
  (`rag.parse`, class ingest) is the second bound (ADR 0007 and §17.1: ingest yields to interactive
  work). Two concurrent parses were exercised only in `TestParserCrashIsolated`.
- **Power:** not measured, no instrument on this box. CPU-seconds are the proxy: parse time plus start
  time per document, which is why start matters more than parse for small files.

## 4 GB profile impact
**Preserves** the 4 GB target (§7, rule 17). No resident parser service, no pool, nothing loaded until a
document is queued; the process exists for one document and one core. The largest peak seen for an 8 MiB
result was 123 MiB resident on Linux and 152 MiB committed on Windows, and the hard cap is the budget,
512 MiB by default, which a 4 GB profile can lower (the floor is 64 MiB; the Windows runtime alone commits
45 MiB). OCR, the one parser-side component that would be heavy, stays off and unbuilt. What it makes
harder: the Windows and macOS levels are L1, so a deployment there leans on the service account's own
privileges, and a Linux 4 GB host needs a kernel that lets Landlock and seccomp apply to reach L2 (the
level is reported either way). The emulated 4 GB run shows no difference in memory and no failure; it is
not certification.

## Re-evaluation trigger
- A measured ingest of many small files in which process start exceeds about 25 % of the time (the
  per-scope pooled worker, ADR 0014).
- An OCR engine being proposed (the adapter must reach L2 or a container; measure RSS and seconds per
  page on a scanned-page corpus before it is enabled by default).
- A macOS or Linux arm64 runner becoming available (every "untested" cell in ADR 0014).
- A new Go release (the Linux address-space baseline moves with the runtime; the limit is relative for
  that reason, but the 64 MiB slack should be re-checked), or `wazero` or Go's `wasm` target closing the
  20 to 60 times gap.
- A hidden-text technique the parsers miss (new fixtures, a parser version bump and a new index
  generation).
- Windows AppContainer becoming cheap (golang/go#80415).
