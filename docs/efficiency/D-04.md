# Efficiency review — D-04: deterministic exact-rule router and dialogue decision stage

Every feature records this before it counts as done.

Host and labels. Every timing is from the dev box: Intel i7-10700K (16 logical CPUs), Windows 11, Go 1.27.1,
`CGO_ENABLED=0`, one process, `go test -run xxx -bench . -benchmem -benchtime 3000x -count 5
./internal/dialogue/decision/` (`bench_test.go`), median of five runs with the range beside it. They are labelled
**emulated-by-construction**: no model runs, the scorer is the instant fake (`internal/decision/fakescorer`), the layer's
audit appender is an in-memory double, and the policy gateway writes its records to a real SQLite audit log in a temp
directory. They are not from a resource-limited container, so they are neither certified nor a latency claim. Corpus
counts are exact (`TestCorpusExactRuleCoverage`, `TestPromptSizeNarrowedBySelection`, `go test -count=1 -v -run
'TestCorpusExactRuleCoverage|TestPromptSize' ./internal/dialogue/decision/`) on `tests/performance/corpus/conversation-v1.jsonl`
(70 cases, 112 turns, clinic-booking reference application, English and Italian).

## Requirement
Put the optional scorer into the §11.1 turn pipeline without letting it decide anything that matters: exact rules first
and the scorer only where they cannot decide; every selected id re-resolved by the deterministic side; a typed fallback
reason and the unchanged controller path for every failure; the controller still realises language, pronouns and
clarification and still owns RAG synthesis; controller calls and generated tokens avoided are counted; with the layer off
or broken every flow gives the same outcomes through the controller.

## No-model / deterministic option
Used first, and it is the default. Measured on the corpus, 112 turns:

| Turn is decided by | Turns | Share | Model calls |
|---|---|---|---|
| the core's exact control phrases (cancel, restart, resume, typed yes, help, reference) | 8 | 7.1% | none |
| the router's refusal (nothing the role may do matches) | 4 | 3.6% | none |
| the client's structured input (choice, confirm, reject) | 16 | 14.3% | none |
| **no model needed, together** | **28** | **25.0%** | **none** |
| the controller (a TaskProposal with typed field values) | 84 | 75.0% | one proposal call each |

This layer's own exact rule (`ExactCapability`: the whole utterance equals a shortlisted capability's id or title, case and
punctuation aside, never inside a sentence, never when two candidates share the phrase) adds **1 of the 84 model turns**
(1.2%) on this corpus: people write requests ("Book Luca Ferri for 2026-10-14 10:30"), not capability names. It does not
skip the controller (see Decision); it skips the scorer and narrows the controller's prompt to one capability.

What is left after the rules, for the 84 model turns, measured statelessly with the real router (a fresh session, the way
the stage sees a first turn):

| Stateless shortlist size | 0 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|---|
| model turns | 7 | 4 | 3 | 54 | 13 | 3 |

- 7 have no candidate yet (they are answers that depend on an active goal, which the stage never touches);
- 4 have a single candidate (nothing to choose: the scorer is not asked);
- 1 is an exact id/title (no scorer);
- **72 are scorer-eligible** (two or more candidates), 3 of them router-decisive. 62 of those 72 are the first turn of a
  conversation, the only place the stage acts (it abstains while a goal is active, so that a slot answer or a topic switch
  is never narrowed away from the controller).

What the scorer must add, on this corpus: **no avoided controller call.** The corpus has 0 turns whose expected intent is
`cancel` or `help` decided by the model (the 8 control turns are exact phrases the core's rules already take), and all 84
model turns are tasks or corrections that need typed field values only the controller extracts. The scorer-backed control
detectors (help, cancel, reject, confirm, consulted only when no exact rule of any kind matches, the utterance is at most 8
words and something can be cancelled or confirmed) can avoid a proposal call only for a paraphrased control act; the
corpus contains none, so the measured benefit here is zero calls and zero generated tokens. The stage's effect is a smaller
proposal prompt: for the clinic package, one turn narrowed from 3 capabilities to 1 builds a **2369-byte prompt instead of
3036 (-667 bytes, about -223 estimated tokens at one token per three bytes, an overestimate)**. If every one of the 62
first turns were narrowed to one capability the upper bound is 135 capability descriptions removed (about 333 bytes each).
That is an upper bound for an accepted selection, not a measurement of any scorer.

## Candidates evaluated
No scorer model is evaluated here (D-05 and the D benchmark matrix do that). The table is the cost of this layer around any
candidate, plus the exact rule it is measured against.

| Candidate | Size | Peak RSS | p50 / p95 | Quality | Licence | Verdict |
|---|---|---|---|---|---|---|
| exact id/title rule (`BenchmarkExactRule`) | code | 488 B/op, 25 allocs | 1.9 us (1.7-2.1) | exact cases only: 1 of 84 model turns | project | default, first |
| stage with the layer off (`BenchmarkStageDisabled`) | code | 0 allocs | 43 ns (38-55) | identical to no stage | project | measured |
| stage, exact id/title, with the mandatory re-resolution (`BenchmarkStageExact`) | code | 120 KB/op, 1.9k allocs | 1.16 ms (1.02-2.01) | exact cases only | project | measured |
| stage, scorer selection accepted, instant fake (`BenchmarkStageScorerSelected`) | code | 244 KB/op, 3.9k allocs | 2.53 ms (2.28-2.65) | not measured | project | measured |
| scorer-backed control detectors | code | one engine request per rule-miss turn | not measured | no corpus turn exercises them | project | in place, benefit unmeasured |
| qualified sub-1B scorer, CLM-v0.1-8B | not measured | not measured | not measured | not measured | see model registry | later D tasks and `tools/decbench` |

The millisecond figures are dominated by the policy gateway that the resolver calls, not by the scorer path: one
`Gateway.Expose` for the guard's checks of a request and one for the final re-resolution, each writing one policy record
to a real SQLite audit log (this world's sink; a deployment's sink is the same log). The exact rule alone is 1.9 us; making
its selection pass the same re-resolution as a scorer selection costs about 1.2 ms, three orders of magnitude more than
the rule and still three to four orders below a controller call, which is why it is kept. A gateway without a sink would
isolate the gateway's CPU from the SQLite write; that split was not measured.

## Decision
Keep the deterministic rules first and the scorer optional, and ship the layer off by default.

- **A stage selection never skips the controller call.** The dialogue core skips the proposal only when the router's own
  top candidate is decisive and a read that takes no fields (`shortcut`), which the stage cannot change. A selection
  narrows the capabilities the controller is offered; the proposal, validation, entity resolution, policy, prepare,
  confirmation, commit and response verification are unchanged. So through this seam the scorer avoids about **0
  controller calls** and about **0 generated tokens** on a stage turn; what it saves is prompt tokens (above). Counting is
  honest: `Snapshot.ControllerCallsAvoided*` counts only turns a control detection ended with no proposal call in the turn's
  own `Trace`, and `PromptCapabilitiesSaved` is measured from the `Trace` (shortlist size minus the capabilities the
  proposal prompt listed). `GeneratedTokensAvoided*` is an estimate: avoided calls times the size of the smallest control
  proposal (33 estimated tokens), never a measurement.
- **Off is exactly no stage.** A disabled layer returns `disabled` before building any request or writing any event
  (`TestDisabledScorerGivesSameOutcomesViaController`: same acts, codes, capabilities, goals and proposal counts, no
  scorer call, no `decision.*` event).
- **Fail closed, always to the controller.** Unavailable, text model in the router role, timeout, malformed output, resource
  gate, low confidence, calibration, shape, guard and re-resolution failures each give a typed reason and the full
  shortlist to the controller (`TestScorerUnavailableGivesSameOutcomesViaController`).
- Rejected: letting an exact match skip the proposal (needs a change to the dialogue core's `shortcut`); letting the stage act
  while a goal is active (a slot answer could remove the goal's own capability from the controller's prompt); consulting the
  scorer on every short utterance (the detectors ask only when something can be cancelled or confirmed and no exact rule of
  any kind matches, because the engine asks its detectors in its own order and a scorer behind `help` would pre-empt an exact
  `cancel`); a second seam for control decisions (the existing `Detectors` are the seam).
- A defect found in D-03 and left for it: `decision.accepted` carries float scores, which the real audit log refuses
  (canonical JSON takes integers only), so against the real `audit.Log` an accepted result becomes an `unavailable`
  fallback (fail-safe, but the scorer can then never be used). These tests therefore use an in-memory appender for the
  `decision.*` events.

What a scorer call must save to be worth it, from D-03's formula, with the measured inputs: on this corpus the controller
call is never avoided, so a scorer pays only through prompt shrinkage (up to about 223 estimated tokens per 3-to-1 turn)
against a request of 2.5 ms of layer CPU plus the scorer's own latency per scored turn. That does not justify a model by
itself; the exact rules plus the controller stay the Lite path until a corpus with paraphrased control acts and a measured
scorer say otherwise.

## Resource impact
- CPU (dev box, emulated): exact rule 1.9 us; layer off 43 ns; exact stage turn about 1.2 ms; accepted scorer turn about
  2.5 ms, almost all of it two policy-gateway calls and their SQLite audit appends. Detector turns add one engine request
  (a guard check with one Expose, then the provider; not benchmarked on its own) only on a rule miss of a short utterance
  with something to cancel or confirm.
- RAM: no goroutine, no timer, no model resident, no cache of its own; the engines are three small structs and a bounded
  result cache inside `internal/decision` (off in these tests). A turn allocates about 120 KB (exact) to 244 KB (scorer).
- Storage: with the layer on, a scored turn writes the engine's `decision.invoked`, `accepted` or `fallback` and
  `final_action` events (identifiers and numbers only) plus two policy records; an exact stage turn writes one policy
  record and no `decision.*` event; off writes nothing. The cost of the real audit append is the main open number.
- Latency: bounded by `min(Config.Timeout, the dialogue engine's decision deadline minus a 25 ms margin)`, so the engine's
  inner call always ends before the outer one and never records an acceptance the pipeline gave up on
  (`TestScorerUnavailableGivesSameOutcomesViaController/a_hung_scorer...`).
- Concurrency: stateless apart from the counters (one mutex); the per-turn state lives in the wrapped turn's context.

## 4 GB profile impact
Preserves it. Nothing here loads a model or starts a service; the layer is off by default, a Lite or 4 GB deployment runs
the core's exact rules and the controller exactly as before, and the code adds no resident memory. Whether any scorer fits
the 4 GB profile is decided by the benchmark tasks, not by this one.

## Re-evaluation trigger
A scorer candidate is qualified (D-05 onward) and its measured latency and acceptance rate can be set against the formula
above; the conversation corpus gains paraphrased cancel, confirm and help turns (today 0 of 84 model turns, so the
detectors' benefit is unmeasured); the dialogue core lets an exact or selected candidate take the no-model shortcut (then
a stage selection can avoid the controller call); or the real audit append cost of the policy records turns out to dominate,
in which case the resolver can share one exposure per turn.
