# Efficiency review — M2-14: RAG evaluation harness and corpus

Every feature records this before it counts as done. The code is
`tools/rageval`, the corpus `tests/performance/rag`. The figures are **dev box** figures (Windows 11, Intel i7-10700K,
16 logical cores, 64 GiB, Go 1.27, `CGO_ENABLED=0`, modernc.org/sqlite, a shared machine with antivirus and other jobs),
**neither emulated nor certified**: the tool applies no cgroup cap, so a result labelled `lite` stands for the Lite profile
(bench's rule: every limited profile is emulated, never certified) and says in `isolation` that nothing was capped. They come
from `go run ./tools/rageval run --embedder fake --corpus tests/performance/rag --out <dir> [--mode fts|hybrid|rerank]` on the
branch while it was being built (the result files record the commit and `git.dirty: true`; the labelled-corpus rows are from
`--scale-sizes none`). The embedder is the **fake** one (a hashed bag of words at 384 dimensions), the answer generator is the
**extractive** one (no model): the run measures the index, the vector scan, the fusion, the authorisation checks and the harness
around the models, never a model. Every result is flagged `synthetic: true`. The machine was shared, so latency cells are ranges
over repeated runs (three for hybrid, two for FTS-only) and a difference of a few milliseconds on a 3 to 5 ms query is not one.

## Requirement
The RAG quality measurement, as a reproducible tool, with the same result envelope as `tools/bench`:

- **Metrics.** recall@k, MRR and nDCG of the evidence package; citation precision; the unsupported-answer rate; exact
  identifiers and terminology; semantic and cross-language questions; tables; conflicting versions; deleted and
  unavailable sources; permission denials and cross-tenant leakage; ingestion throughput and index size; p50/p95
  latency; peak memory.
- **Latency by scope size.** ADR 0032 measured that one large scope dominates the p95 and that a corpus-wide figure hides it,
  so the tool reports 1,000, 20,000 and 50,000 chunks per scope **and** the corpus as a whole, in one database.
- **Corpus.** Synthetic (no real data), English and Italian: exact identifiers, tables, two documents that exist in two
  versions, a stale, an unavailable and a deleted source, a source readable by one principal only, a second tenant, near-miss
  distractor documents, and labelled questions of every kind, including questions that must be declined.
- **Fail closed, deterministic authority.** The judge reads its ground truth from the corpus manifest, not from the system under
  test (a catalog that grants too much must show up as a leak: `TestJudgeDetectsAnAuthorisationLeak`). An error is a failure of
  every metric it touches, never skipped. The generator is blind to the labels, or the answer metrics would be perfect by
  construction.
- **Footprint.** A dev tool: it must run in about a minute with no model, no container and no network, and its temporary
  database must be removed.

## No-model / deterministic option
This is the first candidate, so it is built, not skipped: the whole harness is the no-model option.

- **Embedder: `fake`** (internal/providers/fake `EmbedVector`, a hashed bag of words). It shares words, not meaning. It costs
  microseconds a chunk and holds no weights. What it cannot do is the point of the per-kind rows: a paraphrase or a question in
  another language is out of its reach (en-sem-01, en-xlang-01, it-xlang-01 and it-xlang-02 are never retrieved by words alone).
- **Generator: extractive** (`generator.go`). It reads the question and the `<evidence>` passages out of the very prompt the
  answer package builds, picks the sentences and table rows that share the most of the question's content words and exact tokens
  (numbers, codes), and returns them as claims citing their passage; it declines when nothing holds at least half of them, and a
  question that names a code is answered only by a sentence that has it. The header of a table is context for its rows and never a
  claim (the first version returned the header row of the warranty table as the best answer to "Which extended warranty option
  exists for the Atlas Mini?" and scored 5 of 6 on tables; it shows how far the answer-stage figures depend on the generator).
  It cannot invent, because every claim is verbatim, and it never sees a label. The cost is that the answer-stage metrics then
  measure retrieval plus the claim check (internal/rag/answer, no model either), not generation: the table below shows the same
  answer figures in every retrieval mode for that reason. What a real controller model adds is owed to M2-15.
- **Judge, metrics, result check: code.** Case, accent and whitespace folding, anchor containment, hand-defined metrics
  (metrics.go) re-derived by `rageval check`. No model grades another model.
- **Index size and throughput** are SQLite page counts and a wall clock; **memory** is the operating system's resident set and
  its high-water mark for the process (Windows `GetProcessMemoryInfo`, Linux `VmRSS`/`VmHWM`), with each phase of the scale
  sweep in its own child process so that a phase's peak is its own.
- **The clock.** On Windows the clock behind `time.Since` ticks about every 0.5 ms (a first run printed answer-stage latencies of
  0.000 and query latencies on a 0.5 ms grid); the tool reads the performance counter there (`watch_windows.go`), after which the
  answer stage reads 0.2 to 0.4 ms.

unless a range is shown, so a rate moves by 2.9 points per question (1 of 35 answerable): this is a mechanism check on a small
corpus, not a quality claim about a model.

**The corpus size still matters for a small scope**, by a factor of about 2.6 to 2.9 in p50. That agrees with the neighbouring
measurements (M2-09's lone 1k scope 6.2 / 8.6 ms; ADR 0032's 100 scopes of 1k, 8 to 11 / 17 to 25 ms) and with ADR 0032's own
claim only in part: "a query costs what its own scope costs, not the corpus" is true against the post-filter control it was written
against (79 / 608 ms for the same shape), not exactly. Not investigated here. The likely part is cache: the working set of 30 or
32 scopes (pages of the full-text index and of the vector generations) does not fit the reader's page cache (2 MB per reader in
the Lite configuration) while a lone 1k scope does, and every query of the rotation lands on a scope it has not touched for several
queries; that is a hypothesis, not a measurement. The sweep exists to make it visible.

The labelled corpus's rate is dominated by the fixed cost of a generation (validate and activate: about 2 ms each, 30 of them) on
103 chunks; the 100,000-chunk rate is the one to plan with. The vectors add 58.5 MB per 100,000 chunks (585 B a chunk: 384
int8 codes and the key) and about a fifth of the build time with the fake embedder, which costs microseconds: with a real model
the embedding stage is the model's. The build child holds a whole scope's documents in memory (up to 50,000 chunks), so its peak
(137 to 150 MiB) is the tool's, not the product's; the product's ingestion is queued and bounded (ADR 0007).

## Decision
The smallest candidate that does the job: **no model anywhere in the harness**, and a deterministic judge. A model is needed only
for the thing under measurement, and that run is M2-15's.

- **Two result files per run, one stem.** `<stem>.rag` is the full result (`rag-result.schema.json`, validated and re-derived by
  `rageval check`); `<stem>.json` is the same envelope as `tools/bench` and carries the questions that must be declined as
  `refusal` cases, where `refusal_correctness` is the unsupported-answer rate's complement (when nothing leaked) and
  `catalogue_conformance` is "nothing the asker may not read reached the package or the answer". Reason:
  `schemas/bench/result.schema.json` is closed (`additionalProperties: false` everywhere), its categories are the four of the
  TaskProposal benchmark and its metrics have no place for recall, MRR, nDCG or latency by scope size; the schema and `tools/bench`
  belong to M0-11 and are reported, not edited. The acceptance command `go run ./tools/bench check <dir>` passes because every
  `*.json` it reads is a valid bench result; the `.rag` extension keeps the full result out of its way (it validates every `*.json`
  against the bench schema). Relabelling a bench metric as a RAG metric (`capability_routing` as recall, say) was rejected: it would
  be a green check that measures nothing it names. `TestEnvelopePassesBenchCheck` runs the real `bench check` on a real run, so
  drift between this tool's copy of the envelope and bench's is caught.
- **Metric definitions** are in the comment of `metrics.go` and tested against hand-worked numbers
  (`TestMetricsAgainstHandComputed`): the unit of relevance is the labelled evidence entry (a document and anchor strings), an
  item is novel when it hits an entry no earlier item hit, nDCG is binary with a log2 discount and an ideal list of
  min(k, entries), unanswerable questions are out of recall, MRR and nDCG and count against the unsupported-answer rate.
- **Scale sweep shape.** One database, scopes of exactly 1,000 / 20,000 / 50,000 chunks plus 29 more of 1,000 (a corpus of
  100,000, the size ADR 0032 measured), each size asked in its own process, the corpus as a whole in one more; counts are asserted
  (`ValidateGeneration` against the number built; `TestRunWithFakeEmbedder`). Sizes, small scopes, query counts and the seed are
  flags. The scale phases always use the fake embedder at 384 dimensions: they measure the index, not a model.
- **`vector_min_score` stays 0.** M2-09 left its calibration to this task. On the fake it moves recall@1 from 0.871 to 0.900 at 0.2
  and cuts cross-language recall at 0.3; a floor is a threshold on a raw model score, so the number belongs to the real embedder
  and is a flag (`--vector-min-score`) for M2-15 to sweep. Nothing in `internal/` was changed.
- **The extractive generator stays the default and the only one** (a LocalAI generator is a follow-up for the run that has a
  controller model). **No reranker adapter exists**, so `--mode rerank` is the lexical reranker and always synthetic;
  `--embedder localai` refuses it.
- **Peak memory is per process**, so the sweep re-executes the tool's own binary (`rageval scenario build|query`, spec on stdin)
  and never anything else; `--scale-in-process` exists for tests and says `isolated: false` in the result.
- **Findings to act on** (not fixed here, outside the scope): (1) the corpus-size effect on a small scope above, for ADR 0032;
  (2) at 50,000 chunks the full-text stage is 212 to 232 of 238 to 258 ms and the vector-only hydration 23 to 24 ms, so the
  per-workspace corpus ceilings and term caps M2-09 designed in are what bound the p95, not the vector stage; (3) cross-language and
  paraphrase questions are the whole case for the embedder, and the corpus has 13 of them (kinds semantic and crosslang), 4 of which
  nothing no-model answers.
- **Rejected:** grading answers with a model (circular and heavy); a generator that reads the labels (perfect by construction); one
  corpus-wide latency figure (it hides the 50k scope by 1.7 to 3.2 times); extending `schemas/bench` from this task (not ours);
  sampling memory with `docker stats` (the tool runs on the host, so the bench envelope's `memory` block is the `none` form and the
  operating-system figures live in the `.rag` file).

## Resource impact
- **Time.** The default run (labelled corpus plus the 100,000-chunk sweep) takes about 62 s with hybrid and 46 to 53 s with FTS-only
  on the dev box: the sweep's build 25 to 32 s / 20 to 23 s, its queries about 30 s, the labelled corpus about 1 s.
  `go test ./tools/rageval/...` takes about 12 s (it runs the real `bench check` once and the sweep at 30 to 240 chunks).
  `--scale-sizes none` is a run of about 1 s.
- **RAM.** The orchestrating process: 28 to 32 MiB. Phases of the sweep: build 137 to 150 MiB, queries 29 to 93 MiB, 30 to 130 MiB
  across the corpus (hybrid, Lite vector cache of 64 MiB; FTS-only holds 29 to 31 MiB at every scope size, so **the vector index
  costs about 36 MiB at 1k, 63 MiB at 50k and 98 MiB corpus-wide in resident memory** at this size).
- **Storage.** 100,000 chunks of the synthetic text: 145.7 MB FTS-only, 204.3 MB with 384-dimension vectors; 1,457 and 2,043 B a
  chunk. The throwaway database is removed after each run (it is also in `.gitignore`).
- **CPU, power, concurrency.** One reader, sequential questions, no background goroutine. Power is not measured.
- **Product latency (what the harness measured, fake vectors, ranges above):** 6 / 8 ms for a lone 1k scope, 17 to 20 / 26 to 34 ms
  for the same scope in a 100,000-chunk corpus, 89 to 119 / 141 to 171 ms at 20k and 241 to 257 / 321 to 373 ms at 50k, hybrid;
  FTS-only 15 to 27 / 30 to 56, 84 to 100 / 134 to 189 and 203 to 230 / 285 to 311 ms. Neither emulated nor certified; the
  labelled-corpus questions take 2 to 7 ms end to end.
- **What is not measured:** a model (embedding, controller, reranker), query embedding latency, the parser, the job queue, more than
  one reader, the experimental-4g vector cache of 0, a run inside the Lite container.

## 4 GB profile impact
**Preserves it.** The harness is a development tool and ships in no binary, no container and no service; it adds no always-on
process, no model and no dependency (`go.mod` is unchanged). What it measured bears on the target:

- **FTS-only holds about 30 MiB at every scope size up to 50,000 chunks** and a 100,000-chunk corpus is 146 MB on disk: the
  no-model pipeline fits the 4 GB profile with a large margin in memory and storage. Its limit there is latency (p95 285 to 311 ms
  at 50k on a fast desktop CPU; the corpus ceilings of M2-09 matter), not memory.
- **Hybrid costs resident memory that scales with the scope**: 65 MiB at 1k, 93 MiB at 50k, 130 MiB across 32 scopes with the Lite
  cache of 64 MiB, plus 58.5 MB of storage per 100,000 chunks, plus the embedding model (Granite Embedding 97M, to be measured by
  M2-15). That is affordable on 8 GB and tight on 4 GB; the experimental-4g profile starts with the vector cache off (M2-09,
  ADR 0011), which this run did not measure, and with it the supported ceiling falls to 25,000 vectors per workspace. The sweep makes
  the cost visible per scope size, which is what the 4 GB decision needs.
- It also makes the hidden-tail argument for per-workspace corpus ceilings measurable: a single 50k workspace has a p95 1.7 to 3.2
  times the corpus-wide p95.

## Re-evaluation trigger
- **M2-15** (the live run: Granite Embedding 97M through LocalAI under `compose.lite.yaml`, FTS-only against hybrid against
  hybrid + a compact reranker if one exists): replace every fake number above, sweep `--vector-min-score`, and add the
  controller-generated answers' effect on citation precision and the unsupported-answer rate.
- A change of the query or answer defaults, the chunker, the index layout (ADR 0032) or the vector provider; a third language; a
  reranker adapter; the corpus growing beyond 50 questions (then the per-kind rates become meaningful to a point).
- Extending `schemas/bench` with a `rag` section and teaching `tools/bench check` to dispatch on it: the `.rag`/`.json` pair can then
  become one file and `rageval check` can fold into `bench check`.
- Understanding the corpus-size effect on a small scope (the cache hypothesis above): reopen the sweep with a reader cache
  sweep when ADR 0032 is revisited.
