# Efficiency review — M3-17: Resource governor (priorities, admission control, idle unload)

Every feature records this before it counts as done.

## Requirement
§17.1/§17.2 and rule 12: background work cannot starve interactive work; work is rejected or queued before memory is
exhausted (process RSS plus provider-reported runtime memory); a model is unloaded after an idle period but never
before a minimum warm period; ingestion pauses under disk pressure before interactive or transactional storage is
endangered (§18); no agent or tool loop is unbounded. Every decision is deterministic, fails closed on an unknown
reading, and never evicts a model as a side effect of admission.

## No-model / deterministic option
This feature is pure arithmetic over injected probes: a budget comparison, a counter of live turns, two timestamps per
model, two disk floors with hysteresis and a step/time counter. No model is involved and none could do better: a
model deciding whether to run a model is circular and costs the memory it is meant to protect. The deterministic
option is chosen; there is nothing larger to evaluate.

## Candidates evaluated
Only deterministic designs were compared (none involves a model, so Size and Quality do not apply). Numbers are from
the dev box (Windows 11, i7-10700K), `go test -bench` with 200000 iterations, not a target host.

| Candidate | Size | Peak RSS | p50 / p95 | Quality | Licence | Verdict |
|---|---|---|---|---|---|---|
| Cached readings, hooks into the existing queue seams (`DequeuePolicy`, ingest `DiskPressure`) | about 1.7k lines of Go with comments, no new table | 736 B allocated per Governor, 448 B per refresh | Policy.Pick 55 ns (103 ns held), Admit+Release 145 ns, Refresh 0.7 us | all five required tests pass | project licence | chosen |
| Poll the OS and the runtime on every call (no cache) | smaller | none | RSS 0.5 us, statfs 31 us, runtime HTTP call: milliseconds, inside the lease transaction | same decisions, but holds the single SQLite writer for the I/O | n/a | rejected: I/O in the lease transaction serialises every enqueue and lease behind it |
| New governor goroutine per class with its own semaphore | larger | one goroutine per class plus stacks | n/a | duplicates the queue's per-class workers and depth limits (M0-06) | n/a | rejected: the job queue already bounds workers and depth per class |

## Decision
Cached readings maintained by one optional loop (`Governor.Run`, one goroutine, one tick every 2 s), read without I/O
by `Policy` (inside the lease transaction) and `BackgroundHold`. `Admit` re-reads only the cheap process RSS itself and
never calls the runtime, so a hung runtime cannot delay a live request. Held background work waits in the durable job
queue (nothing is spent on an attempt), live work that does not fit is rejected with a typed `resource_exhausted`.
Background work may use 70 % of the budget; the rest is an interactive reserve. Models are unloaded only when idle for
15 min and warm for 2 min (both configurable, idle >= warm enforced), never when pinned or in use, at most four per
sweep. The runtime-specific halves (reporting memory, unloading) are optional interfaces for the LocalAI adapter, not
a change to `internal/providers`. The disk guard pauses at 2 GiB free, resumes at 3 GiB, calls 512 MiB critical, and
treats an unreadable volume as pressure.

## Resource impact
- CPU: Policy.Pick 55 ns, 0 allocs (103 ns, 0 allocs while held); Admit then Release 145 ns, 32 B; Refresh 0.7 us
  with a fake runtime; real probes cost 0.5 us (process RSS) and 31 us (statfs, cached per 2 s). One tick every 2 s
  is well under 0.01 % of one core. Measured on the dev box.
- RAM: a Governor is 736 B at construction plus one small struct per loaded model (a handful); no buffers, no
  unbounded maps (the model table follows the runtime's report, the unloaded set is bounded by what was ever loaded).
- Storage: none. No table, no file, no log beyond level changes and unload events.
- Latency: no I/O is added to a live request (RSS syscall at most once per 2 s). Idle unload trades a cold load on the
  next request for memory: `Stats.Unloads`/`Stats.Reloads` count it so a soak run can tune `idle_unload_after` and
  `min_warm`.
- Concurrency: one mutex over a few integers; Policy and Admit hold it for tens of nanoseconds. Background reservations
  are capped at 70 % of the budget, so the interactive reserve is never reservable by background work (background heap growth
  can still push a live Admit over budget, which then rejects typed). The reverse (a stream of live turns holding background work forever) is the
  intended §17.1 behaviour, and a handler's wait is bounded (30 s by default) and returns a retryable error.
- Power: one wake-up per 2 s while Run is running; nothing else runs.

## 4 GB profile impact
Preserves it and helps it. The governor is what makes a small budget enforceable: set `memory_budget_bytes` for the
profile and an over-budget model load or turn is rejected before the host swaps, background work is confined to its
share, and an idle model's memory is returned. It adds no service, no model and under 1 KB of state.

## Re-evaluation trigger
When `adapters/localai` implements `MemoryReporter`/`Unloader` (M3 follow-up) and a real-host soak run (M5-11)
reports the eviction/reload rate and the budget headroom, retune the defaults per profile. Also reopen on a runtime
that reports per-request memory (admission estimates could then be measured, not declared), and on any new
background job class.
