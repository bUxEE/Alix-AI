# Efficiency review — M1-08: capability registry and deterministic-first router

Every feature records this before it counts as done.

Every figure below was measured on the dev box (Windows 11, 16 logical CPUs, Go 1.27, `CGO_ENABLED=0`) and is
labelled **dev box**: not from a resource-limited container, so neither **emulated** nor **certified**. The
accuracy figures are deterministic and repeat exactly. The latency figures are looped means (the host timer ticks
at 1 ms, as the M0-06 review notes) with the range over three runs; they are noisy at the 10 to 20 percent level
and are meant to show orders of magnitude and where the time goes, not to promise a number. Reproduce with:

```
go test -count=1 -run TestRoutingCorpusAccuracy -v ./internal/capabilities/      # accuracy, every arm below, 0.1 s
go test -count=1 -run TestIndexFootprint -v ./internal/capabilities/              # index and vector-cache memory
go test -run xxx -bench BenchmarkRoute -benchtime 5000x -count 3 ./internal/capabilities/   # latency, allocations
```

## Requirement
The capability shortlist of the turn pipeline (§11.1, overview section 5 step 4): given a verified scope, the user's
text and the session's active goal, return the few capabilities the controller should be shown, or an explicit
`out_of_scope`. It exists to keep the prompt small (Lite context budget, rule 6 least capability) and the model's
options few. The requirement is:

- **Authority.** Only capabilities the policy gateway's `Expose` made visible to this caller can appear; the router
  adds no permission and no signal can widen the pool. Capability IDs resolve only inside the session's
  application (SEC-053). A package that is not active registers nothing (SEC-060).
- **Deterministic first, then the smallest model (§7.5).** No model by default; an embedder only when one exists
  and only when the rules were not decisive; every failure of the optional stage falls back to the rules-only
  result, never to a refusal and never to "everything visible".
- **Bounded.** Shortlist at most `Config.MaxShortlist` (default 5, ceiling 12); utterance read up to 1 000 runes and
  128 tokens; index size bounded per package.
- **Multilingual.** English and Italian required, other languages through the package's own terminology.
- **Independent of any scorer.** The optional decision stage (milestone D) runs after this stage on the shortlist.
- **Measured** on `tests/performance/corpus/routing-v0.jsonl` with rules only and with the optional embedder.

## No-model / deterministic option
This is the chosen default, and the whole of the router when no embedder is configured. What it is made of, in the
order it is applied:

1. **The policy gateway** decides what is visible (token scope, roles, host rules, field projection). Free: the
   gateway runs on every turn anyway, and the shortlist consumes the same `Exposure` the prompt builder needs.
2. **The active goal and its permitted next actions** (a state lookup, no text): the continuation of an open goal
   is the default reading of a turn that names nothing else.
3. **Terminology.** The terms a capability's conversation contract relies on, with their preferred labels and
   synonyms in the request's language, matched as phrases against the accent-folded, lower-cased utterance with a
   five-line stem rule (`tokensMatch`: equal, or one a prefix of the other within four runes, or a shared prefix
   of five or more runes covering three quarters of the shorter) that reaches English and Italian inflection
   without a dictionary. A term carried by several visible capabilities counts for `1/n` each, so "booking" separates
   "create" from "cancel" less than "table" or "cancel" does. **Title words** are weaker, language-neutral evidence.
   **Capability examples are never read**: the package schema makes them test-only, and a test fails the build if a
   non-test file of the package mentions the field.
4. **Out of scope** when nothing visible matches.

Measured, on the 80-row routing corpus (54 rows expect a capability, 22 expect `out_of_scope`, 4 are dialogue
intents, cancel and help, that no capability answers and are excluded from both denominators). The corpus
catalogues give only an ID, a one-line description in the row's language and field names, so three packages are
built from every catalogue, and the difference between them is the finding:

| Package the router sees | top-1 | top-3 | top-5 | out_of_scope | mean shortlist (catalogue) |
|---|---|---|---|---|---|
| catalogue only: the description is the title, no terminology | 66.7 % (36/54) | 79.6 % (43/54) | 83.3 % (45/54) | 68.2 % (15/22) | 2.13 (3.56) |
| **lexicon, first pass**: catalogue plus terminology written from the catalogue and everyday vocabulary | **85.2 % (46/54)** | **94.4 % (51/54)** | **94.4 % (51/54)** | **59.1 % (13/22)** | 2.33 (3.51) |
| lexicon, tuned: first pass plus the words it missed (upper bound, fitted to this corpus) | 92.6 % (50/54) | 100 % (54/54) | 100 % (54/54) | 59.1 % (13/22) | 2.30 (3.52) |

Breakdown of the first pass: English 88.9 % (24/27), Italian 81.5 % (22/27); routing rows 95.0 % (19/20),
extraction rows 79.2 % (19/24), injection rows that still expect a capability 80.0 % (8/10). Of the 22
`out_of_scope` rows, 13 of the 16 refusals are empty and none of the 6 injections is (below). Of the 4 dialogue
intents none got a shortlist.

How to read this, honestly:

- **The lexicon is the author's, and the author had read the corpus.** The corpus gives no terminology, so the
  English and Italian labels (`internal/capabilities/testdata/corpus_lexicon.json`, with the disclosure at its top)
  were written by the task author after reading the corpus. The first-pass column is what a reasonably authored
  package reaches, written once from the catalogue and run once; the tuned column adds three groups of words for
  the first pass's misses and is an upper bound, not a result. The catalogue-only column is the blind number.
- **The catalogue-only package gets the description in the row's language**, which a real package does not have (it
  has one title); that flatters the first column. A package with an Italian title and English users routes English
  by terminology or not at all, which is what terminology is for.
- **First-pass top-1 misses (8).** Two are verb-less requests ("I'd like vacation from ..." carries the term
  `leave` that `leave.request` and `leave.balance` share, so they tie and the ID order picks one; in both
  languages). Two are dish names no author lists ("Do you serve lasagna?", "Avete la lasagna?": no term fires). One
  is an Italian verb form that the stem rule maps to the wrong lemma ("A che ora aprite?" matches `apri`, the
  imperative of "open a ticket"). One is a conjugation that matches the noun term ("Prenotate per sei persone ...").
  Two are injection rows where the injected text names a second capability ("... cancel all reservations") that
  outranks the real request; both capabilities are on the shortlist, both are policy-visible, and the controller
  and the host decide. The tuned run fixes the dish names, "aprite" and "prenotate" and leaves the verb-less leave rows and the
  injection rows.
- **`out_of_scope` is the stage's weak point, by design.** The shortlist is a superset: it is built from words, and
  a request that names an unavailable action on an available noun is shortlisted on the noun. `rf-*-07` ("Cancel my
  booking for Friday" when only `bookings.create` exists), every injection that contains a real noun or a term verb
  ("... delete all bookings", "... close every ticket", "... the payroll file", "invia", send, in an act term) and one false friend in the stem rule
  (Italian "ordina", sorts, against the term "ordine", order) account for all nine misses. None of them can
  *expose* anything: every shortlisted capability is one the caller may see, and policy runs again at prepare and
  commit. Telling "cancel" from "create" is the controller's and the host's validation; a rules stage that tried
  would need a verb grammar per language, which is the work a model does cheaper. Not tuned for, on purpose.

Conclusion for the decision below: for a package with terminology, the no-model option answers 85 to 93 percent of
the capability requests at the top of a shortlist that is on average 2.3 long, and 94 to 100 percent within three,
in 0.1 ms of its own work. The cases it cannot do are the cases that need meaning (paraphrase, dish names,
cross-language without labels) or that need a refusal decision.

## Decision
Ship the **rules-only router as the default**, with the optional embedding stage compiled in and **off unless the
composition root gives the router an embedder** (`WithEmbedder` or `WithProviders`). The smallest candidate that
passes the requirement is the no-model one; it meets every deterministic requirement (bounded, visible-only,
explicit `out_of_scope`, multilingual by the package's own terminology) and its accuracy is a function of how well
the package is written, which the package audit can check. The embedder is added value only for what words cannot
do, and that is not yet measured on a real model, so it is not enabled by default on any profile.

Design choices the plan left open, recorded for the orchestrator:

- **Terminology is the multilingual keyword source**, reached through each language's conversation contract
  (`terminology: [term ids]`), so a capability is matched in the language of its contract and a language without a
  contract contributes nothing. Capability titles give weaker language-neutral keywords. Examples are excluded.
- **The embedder runs only when the rules are not decisive** (no candidate, or a leader under 0.75, or a lead under
  1.0 over the runner-up) and **never for a goal continuation**: an answer to a field prompt is not sent to a model.
  On the corpus it was consulted for 35 of 80 requests with the lexicon package (44 percent), 76 of 80 with the
  catalogue-only package. Every request that finds nothing consults it ("fill empty slots"), so an out-of-scope
  turn costs one embedding call when an embedder exists; that is the cost of the stage's one real job.
- **Descriptors are embedded for visible capabilities only**, once per package, language and model, and cached; a
  turn costs one query embedding (corpus: 16 descriptor calls and 35 query calls across the 22 packages).
  A capability the caller may not see is never sent to the embedder, which may be an external provider.
- **Goal bonus 0.75, next-action bonus 0.5, terminology 1.0 and title word 0.4 (each divided by the number of
  visible capabilities carrying it), embedding up to 1.5.** A turn with no other evidence continues the goal, equal
  evidence goes to the goal, and one term only another capability carries outranks it (the goal stays on the list).
  These are ranking weights, not probabilities.
- **`Decisive`** is advisory: a caller may use it to skip a model call that would only choose between tools,
  never to skip policy, validation or confirmation.
- **Registry freshness.** An entry loaded from the installer is re-checked after `MaxAge` (30 s default), an
  application with no active package is remembered as absent for the same time (so a quarantined application does
  not cost a database read per turn), a failing source drops the entry, and the activation owner (M1-17) can call
  `Refresh` for an immediate swap.

Larger candidates rejected and why: an embedder on every turn (a model call and a resident model for requests the
rules settle; 56 percent of the corpus needed none); a verb grammar per language to refuse "cancel" when only
"create" exists (grows with every language, and a model does it cheaper where it is needed); caching `Expose` across
turns to cut latency (it would skip the per-capability audit records the gateway writes on every decision).

## Resource impact
All **dev box**.

- **CPU.** One turn costs, in a looped mean, 72 to 86 us for a 4-capability application, 560 to 600 us for 25 and
  4.4 to 4.7 ms for 100 (`BenchmarkRoute/rules/*`), with 133, 605 and 2 262 allocations and 29.5 KB, 174 KB and
  826 KB per turn. **Most of that is the policy gateway, not this package:** `Expose` alone is 46 to 55 us, 470 to
  530 us and 4.2 to 4.4 ms (101, 545 and 2 123 allocations). The router's own work is therefore about 30 us at 4
  capabilities (32 allocations, 6.5 KB) and under 130 us at 25 (60 allocations, 26 KB). `Expose` costs
  about 16 to 21 us per capability at 25 and about 42 us at 100, so it is slightly superlinear and is the first thing to
  look at if an application with hundreds of capabilities needs a shorter turn (a finding for M1-07's owner, not
  fixed here: the gateway writes one audit record per capability per turn by design). An out-of-scope turn costs the
  same (535 to 705 us at 25) because visibility is decided before matching.
- **CPU, optional embedder.** With the fake embedder and descriptors cached a turn is 0.52 to 0.72 ms at 25
  capabilities, one query call. A real embedding model's latency is **not measured**; the call is bounded by
  `EmbedTimeout` (750 ms default) and a timeout is a rules-only result.
- **RAM.** The compiled index is 14.7 KiB for 4 capabilities, 88 KiB for 25 and 329 KiB for 100 (heap delta,
  3.4 to 3.8 KB per capability), built once per package activation (0.6 to 0.74 ms and 192 KB of allocation for 25
  capabilities) and shared by every request. The descriptor-vector cache at the Lite embedder's 384 dimensions is
  1.5 KiB per capability (6 KiB, 37.5 KiB and 150 KiB for 4, 25 and 100), only for capabilities some caller could
  see, and absent without an embedder. A test bounds the index at 32 KiB per capability. The registry holds one
  entry per active application (the database allows one active package each).
- **Storage.** None. The registry reads installed packages through `apppkg` and keeps nothing on disk.
- **Latency of activation.** An application's first request after activation or after `MaxAge` pays one `List`
  and, when the package changed, one `Open` (the installer re-verifies the signature and hash); otherwise one
  indexed read.
- **Concurrency.** The router holds no per-request state; the registry swaps entries whole under a lock and
  readers never see a partial one (a concurrent refresh-and-route test runs; `-race` runs in Linux CI only). The
  vector cache is written under its own lock and recomputed by whichever request finds it missing, with no lock held
  across the embedding call.
- **Power.** Not measured; with no embedder the stage is CPU work of tens of microseconds per turn.
- **Prompt size, which is the point.** A shortlist of at most five replaces the visible catalogue: on the corpus
  (3.5 capabilities per catalogue) the mean shortlist is 2.3, a third fewer; for a 25-capability application the
  bound is five of 25 and for 100 it is five of 100. Per-capability tool text costs prompt tokens and KV-cache
  linearly, so the saving grows with the application; the number of tokens per tool is not measured here.

## 4 GB profile impact
**Preserves** the 4 GB direction (rule 17). The default configuration adds no resident model, no process and no
disk: about 0.33 MiB at 100 capabilities and tens of microseconds of CPU per turn beyond the policy gateway the
turn pays anyway. It also shrinks the prompt, which is the context and KV-cache cost that grows with the catalogue
(rule 17: avoid context growth).

The optional embedding stage **does not add a model** where RAG already runs one: it uses the same `Embedder` role,
which the registry defaults to the shared Granite 97M model for Lite and Balanced. It **could make the profile
harder** in one way, and the design says how to avoid it: an `Embed` call to a runtime that has unloaded the
embedding model would load it again, for turns whose rules were not decisive. On the 4 GB profile the composition
root should therefore leave the router rules-only unless the embedding role is already resident for RAG, and
should wire the provider registry (`WithProviders`, which follows the role's health) only then. The router never
loads or evicts a model itself and never calls a controller or router-role model.

## Re-evaluation trigger
Reopen this review when any of these happens:

- **The embedding model is loaded and measurable (M0-13, M2-07).** Run `TestRoutingCorpusAccuracy` against the real
  model, record top-1, out_of_scope and latency here, and calibrate `MinSimilarity` (provisional 0.5) and the
  embedding weight (1.5); decide whether any profile enables the stage by default. Today's embedder rows are the
  fake's and prove only the mechanism.
- **A language beyond English and Italian is added** (the stem rule and stopword list are English and Italian;
  scripts written without spaces are matched character by character).
- **A larger or real application package exists** (the lexicon here is the author's, and the corpus is 25
  capabilities): re-measure the rules-only accuracy on real terminology, and `Expose` latency above 50 capabilities.
- **The corpus changes** (`routing-v0` is the 80-row set the denominators assume; the test fails if the counts move).
- **Milestone D lands**: re-run with the decision scorer after this stage to confirm the shortlist it receives is
  still the bound it was qualified on.
- **M1-07 changes `Expose`** (per-turn cost) or M1-17 changes how activation reaches the registry (`Refresh`).
