# Efficiency review — M3-18: the dialogue engine adopts the bounded context builder

Every feature records this before it counts as done.

All figures were measured on the Windows 11 dev box (Intel i7-10700K, 16 logical CPUs) with Go 1.27,
`CGO_ENABLED=0`, SQLite (`modernc.org/sqlite`) on the box's temp disk, and are labelled **dev box**: they
are not from a resource-limited container, so they are neither **emulated** nor **certified**. **No model
runs in this task**: the provider is the deterministic fake. Every prompt size is in
`providers.EstimateTokens` units (one token per three bytes, rounded up; "est toks") and comes from the
real prompts the real engine sent (router, policy gateway, session store, coordinator, host fake,
verifier; only the model is scripted). Anything about real tokens, inference time or KV memory is
**arithmetic from the ratios and rates of `docs/operations/resource-budgets.md`, not a measurement**, and
is labelled so. The conversation is synthetic (below): it exercises the bounds, it does not measure how
well a model answers from the context.

Repeat the measurements:

```
go test -count=1 -run TestLongConversationStaysWithinProfileBudget -v ./internal/dialogue/   # after: 500 turns, every profile
go test -run xxx -bench BuildProposal -benchmem -benchtime 2000x -count 4 ./internal/dialogue/ # builder cost
go test -count=1 ./internal/dialogue/...                                                       # all tests of the package and of dctx
```

"Before" is the engine of `main` (5eb6baa), which is also the engine of commit `8b5457f` of this branch: that
commit adds only a test driver, `internal/dialogue/longconv_test.go`. To reproduce the "before" figures, run
`git archive 8b5457f go.mod go.sum internal pkg schemas` into a scratch directory, **overwrite its
`internal/dialogue/longconv_test.go` with the one of the final commit of this branch** (the final driver numbers
its model-bound utterances, `#017`, and the figures here are for that script; the driver of `8b5457f` has no
markers and gives 1,011 mean / 1,058 max at the plateau), and run a throw-away test that calls `newLongConv(t)`
for 500 turns and logs `proposalCall(res).PromptToks` and `ModelCall.TurnsReplayed`. With that file the driver is
the same in both trees; the engine code is not.

## Requirement
§11.3: the model's context is the session state (active and suspended goals, slots, the pending
clarification, bounded relevant turns, compact completed-goal capsules); "the full transcript is stored
separately from the model context. Old turns are not repeatedly replayed." §17.2: "one bounded context per
active request; capped prompt, output and tool-schema tokens". M3-03 built that context
(`internal/dialogue/context`, package `dctx`); the engine of M1-14 still assembled its own prompt with its own
`MaxRecentTurns` and `MaxTurnRunes`. For this task:

- every proposal prompt of the engine is built by `dctx.Builder.Build`, within the budget of one profile
  (`Config.Profile`, Lite by default), and the engine has no limit of its own beside it;
- what of the session state the model may see is decided by the policy gateway's decisions of the turn
  (`Visible(capability, field)`), including capabilities that appear only in capsules or goals set aside;
- the fence gap of M1-14 is closed: a replayed assistant reply that contains `</earlier_reply>` cannot close
  its own fence;
- the caps of `resource-budgets.md` 6.2 that had no enforcement point and belong to the engine are wired, the
  rest are listed as follow-ups;
- prompt size before and after is compared on a 500-turn conversation.

## No-model / deterministic option
**Chosen, and nothing was added that needs a model.** Everything here is plain Go over `sessions.State`, the
bounded recent window and the policy gateway's decisions. The two model-shaped alternatives were rejected
already, with arithmetic, in `docs/efficiency/M3-03.md` (model summarisation of old turns; an embedding-ranked
window) and nothing in this task's measurements changes that: no corpus run exists yet that shows a reference
lost to the lexical selection.

What changed in the engine, and what it costs:

| Part | Before (M1-14) | After (this task) |
|---|---|---|
| Replayed history | the last 6 rows of the window, each clipped to 240 runes, whatever they say (`MaxRecentTurns`, `MaxTurnRunes`) | `Builder.Window` reads the newest `CandidateRows` (24 on Lite) rows; the builder replays the newest 2, the rows the state points at and the rows that share words with the turn, best 6, each clipped to `MaxRowRunes` (240); a token cap of its own for everything from history (`MaxHistoryTokens`, 384) |
| Session state shown | the goal, its visible slots, the last act | the same, plus the goals set aside (about 22 est toks a line) and the completed-goal capsules (about 61 est toks a line, older ones folded into one digest line) |
| What is visible | `Decision.VisibleFields` of the goal's capability if it was among the (decision-stage-narrowed) candidates, else no slot values | `Visible(capability, field)` from the gateway's decisions: the router's own for the shortlist, one fresh `PhaseExpose` decision per other capability the state names; a denied or undeclared capability is not named at all |
| Cut order over budget | oldest turns, choices, capabilities | selected rows that are not the newest, capsule digest, capsules, goals set aside, the newest rows, choices, capabilities (`dctx.Report.Trimmed`; **`recent_turns` is new**) |
| Budgets | `Config.MaxPromptTokens`, `MaxProposalTokens`, `MaxResponseTokens`, `MaxUtteranceRunes`, `MaxRecentTurns`, `MaxTurnRunes` | `Config.Profile` only (one `dctx.Profile`); the six fields are gone, not stacked |
| Output-constraint cap | none | `Profile.MaxConstraintTokens` (380 on 4g, 540 elsewhere): the builder describes fewer capabilities until the constraint fits; if one does not fit, `validation_failed` (`max_constraint_tokens`) and nothing is sent |
| Response-prompt cap | none | `Profile.MaxResponsePromptTokens` (512 Lite) through `Profile.ResponseBudget()`; over it the response call is not made and the reply is the template of the same directive |
| Shortlist | whatever the router returned (default 5, ceiling 12) | the profile's `MaxShortlist` (3 / 5 / 8 / 12): the router the engine builds is configured with it, the engine cuts the candidates to it (a router handed in through `Deps` included) and so does the builder |
| `earlier_reply` fence | `fenceBreak` of `prompt.go` did not list it | listed (the five tags of `dctx`'s fence); the replayed rows themselves are fenced by `dctx`, which already listed it |

Smallest first. Sizes are est toks of the **proposal prompt of the demo application's engine** (frame of 3

described below. "Real" is arithmetic, not measured (see Calibration).

|---|---|---|---|---|---|---|
| Whole-transcript replay (what §11.3 forbids) | about 35,000 est toks at turn 500 (the transcript rows alone are 33,950) | grows with the conversation | n/a | n/a | n/a | rejected: unbounded context (rule 17) |
| M1-14 engine: goal only, last 6 rows clipped | **1,016 / 1,063**; flat from turn 41; no capsules, no goals set aside | none | builder 43 to 78 us | recency only: a goal set aside or completed is forgotten | in-repo | superseded by the next row |

Every figure is the mean (and max) over the 7 proposal calls of ten turns of the script, at turn 500 and at turns
41 to 50 and 91 to 100 (identical after turn 41: the plateau). The same number for all 500 turns: before mean
1,015.4 / max 1,063 over 350 proposals; after mean 1,168.0 / max 1,210. The two builds see the same conversation:
the script sends the same utterances, the fake model answers the same, and
`TestExistingDialogueBehaviourUnchanged` shows the engine reached the same acts, goals, capsules and host writes
turn by turn (below).

## Decision
**Adopt `dctx` with the Lite budget as the engine's only budget; keep the six replaced limits out of `Config`.**
The smallest candidate that meets the requirement is deterministic compaction, and it is already written. The
price is +155 est toks on the Lite proposal prompt at the plateau, which is the new context (3 capsule lines,
a digest line, 3 goals set aside, and selected rather than newest rows), bounded by the history cap whatever the
conversation length. The 4g profile gives the M1-14 size back (below).

The 500-turn conversation: the real engine at `level2` (a write needs a confirmation), a demo application with
`items.get` and `items.create`, one user, one session, 10 turns per cycle: create with a quantity (a confirmation
is requested), look an item up (the create goal is set aside), "go back to the create item" (resumed, a new
confirmation), confirm (committed, capsule), look up again, create with a missing quantity (asks), supply it
(prepares), look up (suspends it), create another, "cancel". By turn 41 the state is full (3 goals set aside, 8
capsules) and stays full. 350 of the 500 turns call the model for a proposal (the rest are resumes, confirmations,
cancels and help, which no model reads).

The test asserts, for every proposal of every profile: the estimate (counted again with the runtime's own
`providers.Budget.EstimateChat` on the request the model received) is within the profile cap, the history part
within its own cap, the rows and the capabilities within the profile, no error; that the mean at turn 500 is no
larger than at turn 50 (within one half row); that every turn marker in the last prompt is one of the newest
`CandidateRows` turns, so what reached the model is the bounded window and not the conversation; and that the
whole transcript is more than three times the cap, so the cap is what holds the prompt. Replaying the transcript
would add 33,950 est toks at turn 500 (the same for every profile), against 377 est toks of Lite history.

Behaviour is unchanged (`TestExistingDialogueBehaviourUnchanged`): the first 30 turns of the same conversation
were recorded on the engine before the adoption (act, goal and phase, goals set aside, capsules, host writes per
turn: for example turn 4 `report_outcome` with 1 write, turn 10 `acknowledge_cancel` with 5 capsules, turn 30
`acknowledge_cancel` with 3 goals set aside) and the test replays them against the new engine; the host's own
call counts (12 prepares, 3 commits, 9 reads, 3 effects) are checked too. Every existing test of M1-14 and M3-02 stayed
green. The edits to existing test files were of two kinds. Setup only (`engine_test.go`, and one line of
`rag_bridge_test.go`): the tests that set `MaxRecentTurns`, `MaxTurnRunes`, `MaxPromptTokens` or `MaxUtteranceRunes`
set a derived profile instead (`ctxLiteWith`), with their assertions untouched. Ported (`units_test.go`,
`perf_test.go`): the tests that called the old `buildProposal` and `assemble` call the new `buildProposal` with a
builder; `TestBuildProposalCutsInOrderAndNeverWidens` changes one expectation, the cut order, which is now that of
the context builder (`turns`, `recent_turns`, `choices`, `capabilities`) instead of M1-14's (`turns`, `choices`,
`capabilities`), and its fixture, whose rows now share words with the message so that the builder's relevance
selection makes them eligible (the old rows were `"word "` repeated); `TestDefaultsAreTheSeedOfTheLiteBudget` now
asserts that the default profile is the Lite seed; the size and benchmark tests build through a builder.

Choices the plan left open, for the ADR owner:

- **`Config.Profile` is one `dctx.Profile` value** (zero means Lite) and replaces `MaxPromptTokens`,
  `MaxProposalTokens`, `MaxResponseTokens`, `MaxUtteranceRunes`, `MaxRecentTurns` and `MaxTurnRunes`. One source
  for the numbers (`resource-budgets.md` 6.2) instead of an override layer: the profile's `Validate` refuses an
  incoherent one, and a profile name is resolved by the composition root with `dctx.ProfileByName`, which is an
  error for an unknown name. The engine's output cap for both calls is the profile's `MaxOutputTokens`.
- **The engine still clips an over-long user message at `Profile.MaxUtteranceRunes`** (`admit`, as M1-14 did) so
  the router, the rules and the prompt read the same bounded text; `dctx`'s own check (a message over the cap is
  `validation_failed`, never clipped) is therefore the backstop and does not fire on a text turn. The M1-14 test
  "user text beyond the bound is cut, not widened" requires the clip.
- **The response prompt is assembled in `prompt.go`**, not by `Builder.Build`: it has no history, state or
  window to select and its host text is fenced as `directive_data` with the engine's own `fence` (the one that gained
  `earlier_reply`). What `dctx` owns is its budget: `Profile.ResponseBudget()` lowers the prompt cap to 512 est
  toks on Lite. The measured response prompts are 330 to 369 est toks, so nothing degrades today.
- **Capabilities that only the state names get one fresh `PhaseExpose` decision each per turn** (never for a
  capability the package does not declare), because the router decides only for the shortlist. Each decision
  writes a policy record (about 1.65 KB, `resource-budgets.md` 5.2): on the 500-turn conversation the policy
  records went from 950 to 1,000 (+0.1 per turn, about +165 bytes of audit per turn); the cost grows with the
  distinct capabilities in capsules and goals set aside (at most 3 + 8 by the store's bounds), not with the
  conversation.
- **Cut order.** `recent_turns` is a new entry in `Trace.ModelCalls[].Trimmed`, and `ModelCall` gains
  `HistoryToks`. Anything that read `Trimmed` for the exact M1-14 words sees `turns` first, as before.

## Resource impact
**Dev box**, deterministic fake model, SQLite with the store's defaults, 500 turns:

| | Before | After |
|---|---|---|
| `BenchmarkBuildProposal` (5 capabilities, 4 typical rows, Lite; 4 runs of 2,000) | 43 to 78 us, 28.7 to 29.0 KB, 191 allocs | 61 to 86 us, 30.4 KB, 210 allocs |
| Whole turn pipeline per turn, fake model (two runs of the 500-turn conversation) | 4.9 and 5.4 ms | 5.5 and 5.7 ms |
| Policy records over 500 turns | 950 | 1,000 |
| Proposal prompt, Lite, plateau | 1,016 est toks | 1,171 est toks |

The builder is tens of microseconds and tens of kilobytes either way, and the whole pipeline without inference
is about 5 ms a turn, against a model call that is expected to take hundreds of milliseconds to seconds on Lite
(estimate, `resource-budgets.md` 7). The cost that matters is prompt tokens. **Estimate, from arithmetic, not
measured**: the measured real/estimate ratios of `resource-budgets.md` 6.1 are 0.75 to 0.83 for message text and
0.49 to 0.57 for whole engine proposal prompts (the output constraint, 275 of the 1,210, is turned into a grammar
by the runtime and costs no real prompt tokens). Applied to the non-constraint text of the turn-499 prompt (935
est toks after, 739 before): about 701 to 776 real tokens after against 554 to 613 before, and by the whole-prompt
band 593 to 690 after. So the new context adds about **147 to 163 real prompt tokens** to a Lite proposal at the
plateau; at the measured prefill rate of the 0.8B on 4 CPUs (118 tokens per second, section 7.1, emulated) that
is about **1.2 to 1.4 seconds** per proposal call, and about 1.7 to 1.9 MiB of KV cache at 11 to 12 KiB per
token. It is the price of "a completed goal is remembered as a line, not as its turns" and of the goals set
aside; the history cap bounds it, and the table above shows the knob (a history cap of 224 gives the M1-14 size
back). The worst case the cap allows on Lite is 2,048 est toks, at most 0.83 x 2,048 = 1,700 real tokens (1,472 when the constraint is the 275 est toks of this fixture)
plus 256 generated, against a configured context of 4,096.

**Memory.** Nothing resident is added; no table, migration, file, process, listener or model. The builder holds
no state between builds and the engine adds one `*dctx.Builder` and two `providers.Budget` values. The heap does
not grow with the history (measured for the builder in M3-03: 95 KiB from turn 50 to turn 500). **Storage:**
none. **Concurrency:** unchanged (turns of one session are serialised; the builder is safe for concurrent use).
**Power:** not measured.

### Calibration of the estimator against the runtime's counts (from `resource-budgets.md` 6.1)
Real prompt tokens measured on the engine's prompts were 0.49 to 0.57 of the estimate for proposals (0.75 to 0.83
for plain text): 391 to 957 real against 787 to 1,814 estimated for proposals of 1 to 12 capabilities. The
estimator therefore errs on the safe side by 20 to 43 percent for text and by about a factor of two for a
proposal, because it counts the output constraint as prompt. Consequences recorded here: (a) the profile caps
are caps on the **estimate**, so Lite's 2,048 est toks admit at most about 1,170 to 1,700 real tokens
(`resource-budgets.md` 6.2), well inside a 4,096-token context; (b) the numbers of this review are estimate
units throughout and must not be read as real tokens; (c) the history lines this task adds are plain text (ratio
0.75 to 0.83), so they weigh more in real tokens per estimated token than the constraint they sit beside, which is
why the real-token cost above is computed on the non-constraint text; (d) the estimator is not to be "corrected"
without a tokenizer (rule R5 of that document), and this task does not.

### Where each cap of `resource-budgets.md` 6.2 is enforced after this task
| Cap | Where |
|---|---|
| Prompt, hard cap | `dctx.Builder` (`Profile.MaxPromptTokens`) and the engine's re-check after a guard (`Engine.budget`); the runtime boundary keeps its own (see follow-ups) |
| Output cap per call | `Input.MaxOutputTokens` zero takes `Profile.MaxOutputTokens`; both calls; `Budget.CheckChat` |
| Shortlist, default | the router the engine builds, `capShortlist` in the engine, the builder (`Profile.MaxShortlist`) |
| Output constraint ("tool schema") | **new**: `dctx.Builder` (`Profile.MaxConstraintTokens`) |
| History | `dctx.Builder` (`Profile.MaxHistoryTokens` and the row, capsule and set-aside counts) |
| User message | the engine clips (`admit`); `dctx.Builder` rejects as the backstop |
| Response prompt | **new**: `buildResponse` against `Profile.ResponseBudget()` |

### Follow-ups, with their owners
- **M0-18** (`deploy/container/localai`, the model definitions and the registry's `context.budget_tokens`): the
  per-profile configured context window (`n_ctx`: 4,096 / 4,096 / 8,192 / 8,192, rule R6) and the resident-role and
  admission checks (rule R3) still have no enforcement point; nothing in `internal/dialogue` can set them.
- **M2-09** (`internal/rag/query`): every RAG cap of section 6.3 (evidence tokens, items, parent expansion,
  candidates per leg, rerank candidates). The evidence is carved out of the same prompt cap, so when it enters the
  engine's prompt the history cap or the response cap has to be re-checked (Lite: 330 + 384 + 1,000 = 1,714 of 2,048).
- **Composition roots** (`internal/cli/cmd_serve.go`; outside this task's scope): select `Config.Profile` from
  the deployment profile with `dctx.ProfileByName`, and give the runtime wrapper `Profile.Budget()` instead of
  `providers.DefaultBudget()` (4,096 prompt, 1,024 output today), so the boundary and the engine enforce the same
  numbers; today the engine's own 2,048 is the tighter of the two.
- **M1-08** (`internal/capabilities`): the router's single hard ceiling of 12 is not per profile; the engine
  already cuts to the profile's shortlist, so this is only about not ranking candidates nobody can show.
- **`docs/operations/resource-budgets.md`** (outside this task's scope): the paragraph "Where each cap is enforced,
  and where it is not yet" and the first row of section 1 still say the engine enforces its own defaults; the
  table above replaces it.

## 4 GB profile impact
**Preserves** the 4 GB direction; it is not evidence that 4 GB works (that stays aspirational until the full
workload passes its gates).

- Context still cannot grow with conversation length, and now this holds for the engine as built, not only for
  the builder: on `experimental-4g` the prompt of the 500-turn conversation is 1,020 est toks at the plateau (cap
  1,536; history 218 of 224) and 1,051 at most, with a shortlist of 3, 4 rows and the 380-token constraint cap.
  By the ratios above that is about 560 to 620 real tokens of text, which fits the 2,048-token context that
  `resource-budgets.md` 6.2 says is enough for 4g and saves 22 MiB of KV.
- The cost of this task on 4g is small because the 4g history cap (224) is the knob that gives the M1-14 size
  back: Lite with that cap measured 1,023 est toks against 1,016 before.
- The new response-prompt and constraint caps (512 and 380 on 4g) are the two that could silently starve a
  package with a large catalogue: a constraint over its cap lowers the shortlist, and if one capability does not
  fit the turn fails with a typed `validation_failed` rather than sending an oversize request. Both are covered by
  tests; a corpus of real packages on 4g is what would show whether 380 is too tight (the measured constraint of
  5 capabilities is 368 est toks, of 12 is 535).
- No resident model, process, listener or table was added; each extra policy decision is a record, not memory.

## Re-evaluation trigger
- **The first M1/M3 conversation corpus run against a real controller model**: replace the estimated tokens
  with the runtime's `prompt_tokens`, measure how often a reference is lost that a larger window, an
  embedding-ranked window or a longer capsule would have kept, and whether the +147 to +163 real tokens of state
  buy answers. Only that measurement can justify an embedder, a summariser, or taking the new lines back out.
- **M0-18 or a composition root selects a profile at runtime**: re-run `TestLongConversationStaysWithinProfileBudget`
  for it and re-check the constraint cap (380 on 4g) against the real package's capability count.
- **RAG evidence enters the engine's prompt (M2-09, M2-10)**: its budget is carved out of the same cap; the history
  cap or the response cap may have to shrink.
- **A package whose capabilities carry many fields**: the output constraint grows with them, and a cap that
  lowers the shortlist is a quality cost this review has not measured.
- **A new language pack**: the stopword list of the relevance selection and the bytes-per-token ratio are English
  and Italian.
