# Efficiency review — M1-21: policy gateway audit batching, one audit event per Expose

Every feature records this before it counts as done.

All timings and sizes were measured on the Windows 11 dev box (Intel i7-10700K, 16 logical CPUs) with
Go 1.27, `CGO_ENABLED=0`, SQLite (`modernc.org/sqlite`, WAL, `synchronous=NORMAL`) on the box's temp disk,
and are labelled **dev box**: not from a resource-limited container, so neither **emulated** nor
**certified**. The box was in use by other processes while the runs were made, which shows in the
spread (the maxima are outliers from that): every figure below is the **median** of eight interleaved runs of the before and the after code
(three of 200 turns and five of 100 turns each), with the minimum and maximum beside it; a quiet batch of
three consecutive runs made first is quoted where it differs. **No model runs in this task**: the provider is
the deterministic fake, so the figures are the cost of the pipeline around inference, not of inference.
Bytes are the length of the stored event data (canonical, redacted JSON), summed from `audit_events`; they
do not include the SQLite page overhead or the WAL.

"Before" is the unchanged gateway (commit `ac5f1e6`, with the final benchmark file copied in), "after" is the
head of this task. Both run the same benchmark file.

Repeat the measurements:

```
go test -run xxx -bench BenchmarkDialogueReadTurn -benchmem -benchtime 200x -count 3 ./internal/policy/policyaudit/
go test -run xxx -bench 'BenchmarkTurnRead$' -benchmem -benchtime 300x -count 3 ./internal/dialogue/         # the unmodified 3-capability benchmark
go test -count=1 ./internal/policy/... ./internal/dialogue/...                                               # the tests
```

`BenchmarkDialogueReadTurn` (`internal/policy/policyaudit/turnbench_test.go`) is the dialogue read benchmark
of M1-14 rebuilt from exported APIs, because the dialogue test kit cannot be imported and has one catalogue
size. It is wired as a composition root wires the engine (the real audit log behind
`audit.NewRecordSink[policy.Record]`, the real policy gateway, the capability router, the action coordinator,
the in-memory host, the scripted model) and runs the same turn ("show me item_1": route, propose, validate,
governed read, directive, verify, persist, audit) on a package of 3, 20 or 100 declared capabilities. The
three are the three of the dialogue kit (`items.get`, `items.create`, `admin.purge`) plus ordinary user
capabilities the turn never asks for. Besides the usual figures it reports the events and bytes the turn
wrote and the time spent inside the audit log's `AppendAt`.

## Requirement
Keep the security properties of ADR-0017 and SEC-087, and stop the audit cost of a turn from growing with the
size of the catalogue:

- every decision is still auditable: for every capability the gateway considered when it chose what the
  model may see, the log still says whether it was allowed or denied, why (the typed code and the fixed reason
  of the check that denied it) and at which effective risk level;
- a decision that cannot be recorded is not made: an `Expose` whose audit append fails exposes nothing, with a
  typed code;
- `Decide` at prepare and commit, the consequential decisions, keeps one full per-decision event each;
- what `Expose` returns, and each in-memory `Decision`, is unchanged; the record is size-bounded (the audit
  log refuses event data above 32 KiB), redacted (identifiers and fixed codes only, never a value or free text)
  and valid against `schemas/policy/decision-record.schema.json`;
- no new model, no cache that skips an audit record (§3 rules 5, 14, 16).

Found by M1-14's CPU profile: `Expose` appended one `policy.decision` event of about 1.65 KB per declared
capability on every turn, about half of a read turn's CPU.

## No-model / deterministic option
This is a pure data-shape change, so the no-model option is the whole solution and no model is involved. The
options weighed, all deterministic:

| Option | Keeps every decision auditable | Verdict |
|---|---|---|
| One event per capability (before) | yes | cost grows with the catalogue: 102 events, 366 KB and about 250 ms of appends per read turn at 100 capabilities |
| Skip the audit of denials, or sample | no: a denial is exactly what an investigator asks for | rejected: breaks SEC-087 and the brief |
| Cache the exposure decision per session and skip repeat records | no: a skipped record is a missing record, and the answer depends on the package, policy and token | rejected: the brief forbids a cache that skips an audit record |
| Record only the allowed capabilities and a count of denials | no | rejected: the denied ones are the evidence |
| **One compact record per `Expose` call listing every capability's outcome** | yes: capability, allow or deny, code, reason, effective risk | **chosen** |
| One event per `Expose` but a full decision record per capability inside it | yes | rejected: the same bytes as before (3.7 KB per capability at 100 capabilities), only fewer transactions |

What the compact record leaves out of a capability's entry (the ordered checks, the field lists, the rules
applied and deferred) is a pure function of the package (named by its version and status), the policy
digests the record carries, the subject and the task fields, so it is recomputable, and it is written in full
by `Decide` whenever the capability is used (prepare and commit). The token's capability list is left out of
the subject for the same reason: it duplicates the outcomes (a capability the token did not permit is a
denial with the reason `capability_not_in_token_scope`).

## Decision
`Gateway.Expose` writes **one exposure record per call** (`alixai.policy-exposure/v1`, a second kind of the
decision-record schema) in place of one decision record per declared capability, and fails closed when the
sink fails.

Design choices, made where the plan left them open (recorded for the ADR owner as well):

- **The record goes through the existing `Sink.Emit(ctx, policy.Record)`.** `policy.Record` is now one of two
  kinds, told apart by `Format`; the compact form is produced by `Record.MarshalJSON`, and a decision record
  encodes byte for byte as before. So every composition root that stores records with
  `audit.NewRecordSink[policy.Record](log, audit.EventPolicyDecision, ...)` gets the gain unchanged: the
  exposure record is stored as a `policy.decision` event whose data says by its format what it is.
- **The audit event type `policy.exposure` is registered from `internal/policy/policyaudit`**, not from
  `internal/policy`: the audit package's own tests import `internal/policy`, so `internal/policy` importing
  `internal/audit` would be an import cycle in test. The sub-package registers the type with
  `audit.MustRegister`, with a `Validate` hook so the log itself refuses a malformed exposure event, and
  provides `policyaudit.NewSink`, the sink that stores decision records as `policy.decision` and exposure
  records as `policy.exposure`. Adopting it is a one-line change in `internal/cli/cmd_serve.go` (outside this
  task's scope; reported to the orchestrator).
- **Batch outcome.** `outcome` is `allow` when the record lists at least one allowed capability, `deny` (with
  the code `permission_denied`) when it lists none; the per-capability outcome, code and reason are in the
  entries. A package-level denial (a quarantined package, a wrong application or tenant) stays a full decision
  record: it has no capabilities and its ordered checks say which check refused.
- **Bounded by construction.** At most 256 entries per record (the capability limit of a package manifest) and
  at most 24 KiB encoded, below the audit log's 32 KiB limit; a larger catalogue is written as several
  numbered parts (`part`, `parts`), so an ordinary catalogue is never refused for its size (a record whose
  subject alone exceeds the budget fails closed: the call exposes nothing and `Exposure.Code` is
  unavailable), and a reader that finds fewer than `parts` records for a call sees the trail is incomplete and
  knows the call exposed nothing: if part 1 is written and part 2 is not, `Expose` returns no capability,
  whatever the `allow` entries of part 1 say. The worst case (256 capabilities with
  127-character IDs, every one denied, and a principal with 64 roles of 128 characters) is 5 events of at most
  22.8 KB, stored through a real log in `TestWorstCaseExposureIsStoredInBoundedEvents`. An ordinary
  100-capability catalogue is one record of 7.1 KB.
- **Decision IDs.** Each `Decision` that `Expose` returns (all of them allowed: the denials are not returned)
  now carries the `DecisionID` of the record that holds it, so a visible decision can be traced to the audit
  event that recorded it; there is no per-capability event to name any more. Nothing outside the policy
  package reads that ID for an exposure decision.
- **`Exposure.Code`** is new and additive: unavailable when the audit record could not be written, the
  package-level code when the package was refused. `Visible` is empty whenever it is set.
- Rejected: a typed `ExposureSink` interface next to `Sink` (the existing sinks, including the audit
  package's own test kits, implement only `Emit(ctx, Record)`, so they would have kept the per-capability
  path or failed closed), and a per-session cache (forbidden).

## Resource impact
**Dev box**, dialogue read turn, real audit log and policy gateway wired as above. Median of eight runs, with
(min to max) over the runs; "policy append" is the time inside `AppendAt` for `policy.*` events, on the one
goroutine that runs the turn, so it is also the CPU of those appends within the benchmark's noise.

| Declared capabilities | | Policy events / turn | Policy bytes / turn | Policy append (ms / turn) | Turn (ms) | Allocated / turn | Policy append share of the turn |
|---|---|---|---|---|---|---|---|
| 3 | before | 5 | 8,175 | 6.8 (5.1 to 40.9) | 10.3 (8.1 to 58.8) | 923 KB, 17.9 k allocs | 66 % |
| 3 | after | 3 | 4,202 | 3.2 (2.5 to 9.4) | 6.4 (5.0 to 16.8) | 643 KB, 11.1 k allocs | 50 % |
| 20 | before | 22 | 43,773 | 36.8 (30.3 to 42.8) | 41.9 (35.5 to 49.8) | 3.66 MB, 78.7 k allocs | 88 % |
| 20 | after | 3 | 5,988 | 4.2 (3.1 to 5.6) | 8.6 (6.0 to 10.2) | 920 KB, 14.7 k allocs | 49 % |
| 100 | before | 102 | 366,493 | 249 (219 to 459) | 264 (232 to 484) | 25.4 MB, 606 k allocs | 94 % |
| 100 | after | 3 | 14,389 | 8.2 (7.3 to 9.5) | 17.0 (14.7 to 19.6) | 2.34 MB, 31.2 k allocs | 48 % |

Total audit bytes of the turn (the dialogue's own `dialogue.turn` event adds about 0.2 KB): 8,410, 44,008 and
366,728 before; 4,437, 6,223 and 14,624 after. The quiet batch of three consecutive 200-turn runs made before
the change agrees: 7.3 to 8.0 ms per turn at 3 capabilities before, 4.9 to 6.3 ms after; 32 to 45 ms at 20
before, 8.0 to 9.2 ms after; 210 to 232 ms at 100 before, 13.1 to 13.8 ms after. The unmodified dialogue
`BenchmarkTurnRead` (3 capabilities, three runs of 300) goes from 6.7 to 7.1 ms and 17.8 k allocations to 6.1
to 8.5 ms (noisy that day) and 11.1 k allocations.

What the numbers say:

- **The audit cost of `Expose` no longer depends on the catalogue.** Before, the cost per extra declared
  capability was 3.7 KB and about 2.5 ms of appends per turn (`(366,493 - 8,175) / 97` bytes; `(249 - 6.8) /
  97` ms), and a 100-capability package spent 94 percent of every read turn in the audit log. After, the
  exposure record costs about 66 bytes per capability (826 B at 3 capabilities, 1,932 B at 20, 7,133 B at 100),
  and the append share of a read turn is about half at every size.
- **What remains is the two full decision records of the turn** (the governed read at prepare and the decision
  for the next suggested action), which are the consequential records the brief keeps whole. Each carries the
  token's capability list in its subject, so they grow with the token: 1.7 KB at 3 capabilities, 3.6 KB at
  100. About half of the remaining policy bytes at 100 capabilities (7.3 of 14.4 KB) are those two records.
  The append time tracks bytes (canonicalisation, redaction, hashing and the SQLite row), about 0.6 to 0.7 ms
  per KB before and after, not the number of transactions, which is why 3 events of 14 KB still cost 8 ms.
- **Latency against inference:** a read turn on a 100-capability package costs about 17 ms of pipeline instead
  of about 264 ms, against model calls expected to take hundreds of milliseconds to seconds on the Lite profile
  (**estimate, not measured**).
- **Gateway CPU outside the log:** evaluating every capability is unchanged (the same checks run for the same
  decisions); the saved allocations (25.4 MB to 2.3 MB per turn at 100 capabilities) are the per-capability
  records no longer built, encoded, redacted and hashed.
- **Storage:** about 3.7 KB per declared capability per turn is no longer written, which at 100 capabilities
  and 1,000 turns a day is about 360 MB a day of audit data before and about 14 MB after (arithmetic from the
  table, not a measurement), and the hash chain is that much shorter to verify.
- **Concurrency:** unchanged. `Expose` is stateless; the appends of different tenants' chains are serialised by
  the store's single writer as before, and one call now holds the writer for one transaction instead of up to
  a hundred, which also shortens the wait of every other writer.

## 4 GB profile impact
**Improves** it and does not make anything harder; this is evidence about CPU, disk and write amplification,
not that 4 GB works (that stays aspirational until the full workload passes its gates).

- No new resident process, model, listener, cache or thread; nothing is added to the heap beyond the compact
  record built per call (7 KB at 100 capabilities, bounded at 24 KiB per part).
- Peak transient allocation of a read turn drops by about 90 percent at 100 capabilities (25.4 MB to 2.3 MB),
  which matters on a small host where the garbage collector and the single SQLite writer are the shared
  resources; CPU and disk write volume per turn fall by the factors in the table, so a small host can serve a
  large catalogue without the audit log setting the turn time.
- The audit database grows about 25 times more slowly per read turn on a 100-capability application, which is
  the difference between a disk-bound and a comfortable small deployment.

## Re-evaluation trigger
- The decision records of `Decide` at prepare, commit and for suggested next actions, which now dominate the
  policy bytes of a read turn on a large catalogue: each repeats the token's capability list (up to 256
  entries) in its subject. A follow-up could record only whether the capability was in the token, or cap the
  list, with a schema change; it is not done here because the brief keeps those records whole.
- Adopting `policyaudit.NewSink` in `internal/cli/cmd_serve.go` (and the test kits that build the gateway):
  re-run the benchmark through it to confirm the typed event type costs the same as the single-type wiring
  measured here, and update any audit reader or export filter that selects `policy.decision` to also read
  `policy.exposure`.
- A package manifest limit above 256 capabilities, or a longer capability ID grammar: `MaxExposureOutcomes`
  and `MaxExposureRecordBytes` follow them (the worst-case test fails first).
- A change of the audit log's event size limit, canonicalisation or redaction: the 24 KiB budget assumes the
  32 KiB limit and a redactor that changes nothing in these records.
- The first multi-tenant load run (M3 and later): measure the writer contention with many sessions, which this
  single-session benchmark does not show.
