# Efficiency review — M0-05: SQLite store (WAL, per-module migrations, FTS5, backup)

Every feature records this before it counts as done.

All numbers below were measured on the Windows 11 dev box (Intel i7-10700K, 16 logical CPUs, 64 GB
RAM, NVMe) with Go 1.27, `CGO_ENABLED=0`, `modernc.org/sqlite` v1.60.1 (SQLite 3.53.4), and are
labelled **dev box**. They are not from a resource-limited container, so they are neither
**emulated** nor **certified**. The memory figures are what the process itself holds (OS working
set), which does not depend on the host's RAM; the timings do. The measurement is kept as a test so
it can be repeated on any host: `go test -run TestMemoryFootprint -v ./internal/store/`
(`internal/store/memory_test.go`; knobs `ALIXAI_PROBE_ROWS`, `ALIXAI_PROBE_CACHE_KIB`,
`ALIXAI_PROBE_READER_CACHE_KIB`, `ALIXAI_PROBE_READERS`, `ALIXAI_PROBE_MMAP_MIB`). It re-executes the
test binary as a child process so the figures are the store's own, read from the OS
(`GetProcessMemoryInfo` on Windows, `/proc/self/status` on Linux), not from `runtime.MemStats`,
which cannot see the driver's allocator. The bare child process is about 9 MiB resident, and every
"growth" figure below is over that pre-open baseline.

## Requirement
One embedded store for all core state (§5.1, §6, §19): transactional and recoverable, WAL mode,
lexical search (FTS5/BM25) with no separate server, per-module migrations that refuse to start on
drift, scope columns and predicates on every table and query (§10.2), online backup, integrity
check. It must keep the Lite profile (8 GB) comfortable and the 4 GB target (§3 rule 17) possible:
bounded page cache, mmap off, one writer plus a bounded reader pool, no always-on extra service.
Safety: fail closed (WAL not enabled, checksum drift, downgrade, missing or malformed scope all
refuse), deterministic authority (no model involved).

## No-model / deterministic option
There is no model in this feature: it is entirely deterministic code, so this section is about the
smallest *infrastructure* that does the job.

- **No database at all** (flat files, or an in-memory map with a log): rejected in ADR 0002 for the
  lack of transactions, FTS and recovery, not on a resource figure. Not measured.
- **Embedded key-value store** (bbolt, Badger): comparable memory, but no SQL and no full-text
  search, so the lexical index and per-table scoping would be built by hand. Not measured.
- **SQLite in WAL mode with FTS5 (chosen).** One file, no extra process, no resident memory beyond
  the caches configured below, and FTS5/BM25 is part of the engine. Measured below.

The cost controls are deterministic decisions, not models: a bounded page cache per connection,
mmap off, `journal_size_limit` capping the WAL at 64 MiB after a checkpoint, a single writer
connection (writers queue inside the process instead of spinning on the file lock), reader
connections released after 5 idle minutes, and a `VACUUM INTO` backup on a short-lived connection
that does not hold the writer.

## Candidates evaluated
Smallest first. First the driver comparison: a throwaway single-connection program (not
committed) with the same workload and pragmas on both drivers: open + create schema (scoped
table, FTS5 external-content index, insert trigger), 10 000 rows of about 200 bytes in one
transaction with the FTS trigger, 1 000 durable single-row commits, 400 BM25 top-10 queries; WAL,
`cache_size=-8000`, `synchronous=NORMAL`, `mmap_size=0`. Three runs of modernc, two of ncruces; a
difference under about 20 % is noise.

## Decision
`modernc.org/sqlite` (ADR 0009), SQLite in WAL mode (ADR 0002), with these defaults:

- **Writer page cache 8 000 KiB, reader page cache 2 000 KiB each, 4 readers**: a page-cache
  ceiling of `8 000 + 4 x 2 000 = 16 000 KiB`. The cache is per connection, so giving every
  connection the brief's `-8000` would have been a 40 MB ceiling with five connections; the split
  keeps the total at the brief's order of magnitude. The five numbers are in the registered
  `store` config section (`cache_kib`, `reader_cache_kib`, `reader_conns`, `mmap_mib`,
  `busy_timeout_ms`; env `ALIXAI_STORE_*`), so a 4 GB deployment selects the Small profile without
  a code change.
- **mmap off.** Measured: with 256 MiB mapped, the 100k-row run held 149.7 MiB warm and peaked at
  212 MiB, against 62.6 and 62.7 MiB, because mapped database pages count in the working set and
  are not bounded by the cache setting. It roughly halves query latency (p50 8.2 to 8.8 ms against
  17.8 to 18.9 ms, p95 126 to 133 ms against 192 to 208 ms), which is a trade a larger host can opt
  into with `mmap_mib`; the Lite default does not.
- **One writer connection** (`BEGIN IMMEDIATE`), `busy_timeout` 5 s plus a five-attempt jittered
  retry on `SQLITE_BUSY`, `synchronous=NORMAL`, `journal_size_limit` 64 MiB. A durable commit
  costs 0.4 to 0.5 ms, comfortable for interactive paths; bulk work must batch (10 000 rows cost
  about 0.7 s with FTS indexing, about 0.1 s without).
- **Hardening pragmas on every connection**: `foreign_keys=ON`, `trusted_schema=OFF`,
  double-quoted string literals off, SQLite defensive mode, UTC. Defensive mode was checked against
  the FTS5 external-content patterns the RAG module will use (insert, update and delete triggers,
  `optimize`, `rebuild`, `integrity-check`); all work (`TestFTS5ExternalContentScoped`).
- **`IntegrityCheck` and `Backup` use short-lived connections.** Found while testing: on a
  long-lived connection that has already used an FTS5 table, `PRAGMA integrity_check` reports
  false "fts5: corruption found reading blob" findings after another connection ran an FTS5
  `optimize`. A fresh connection does not, ordinary `MATCH` queries are unaffected, and it also
  keeps a long check off the pooled readers and the writer.

Larger candidates rejected: the Large profile costs +164 MiB peak for a p50 gain of about a third
(11.2 to 12.6 ms against 17.8 to 18.9 ms) and no p95 gain (190 to 197 ms against 192 to 208 ms) at
100k rows; at 4 GB that memory is the point. A second FTS engine or an external search server stays
out of the baseline (§5.1).

## Resource impact
- **RAM, steady**: about 3 MiB after open and migrate. The default page-cache ceiling is 16 MB;
  with four concurrent readers the warm working set grew by 39 to 40 MiB at 10k rows and by 54 MiB
  at 100k, and the peak including a backup was +46 to +54 MiB. The Small profile grows by 17 to
  19 MiB. The excess over the cache budget (about 3x) is the driver's allocator overhead, FTS5's
  in-memory term buffers and sorter space for `ORDER BY bm25`, so the cache setting is the lever
  but not the whole number.
- **RAM, transient**: a 100 000-row single transaction raised the working set to 34 MiB (Default)
  and 22.7 MiB (Small); dirty pages spill to the WAL past the cache size. A backup adds about
  7 to 9 MiB while it runs (its own 2 MB cache plus the VACUUM working set) and releases it on close.
  Idle reader connections are closed after 5 minutes, which drops their caches (by design, not
  measured separately).
- **CPU**: `ORDER BY bm25()` scores every match, so a query made of very common terms costs in
  proportion to the posting lists. In this synthetic Zipf corpus (a few terms occur in most rows)
  the two-term AND queries drive the p95 tail: 18 to 20 ms at 10k rows, 192 to 208 ms at 100k. The
  tenant predicate on an `UNINDEXED` FTS column is applied after the match, so it does not shrink
  that work. This is a finding for the RAG task (M2): cap candidates, prefer selective terms, or
  use per-tenant FTS tables if large single-index corpora appear. It is not a store defect.
- **Storage**: 58.6 MiB for 100 000 rows of about 200 bytes plus a second 100 000-row plain table
  (about 0.3 KB per row per table including the FTS5 index on the first); the WAL stays under
  `journal_size_limit` after a checkpoint and is removed on clean close; a backup is one
  self-contained file of the same size as the database.
- **Latency**: durable commit 0.4 to 0.5 ms, `Open` 25 to 36 ms, a backup 0.15 s for a 6 MiB
  database and 1.5 s for 59 MiB.
- **Concurrency**: readers never block on an open write transaction and never see uncommitted rows
  (`TestConcurrentReadersSingleWriter`); writers serialise in-process with no `SQLITE_BUSY` between
  them (`BusyRetries == 0` in that test) and retry only against another process.
- **Binary**: +4.6 MB stripped for the driver. **Power**: not measured; the store starts no
  background threads or timers (no polling, no auto-vacuum job).

## 4 GB profile impact
**Preserves** the 4 GB target. The store is a library inside the existing process, with no second
service, and its memory is a configured, bounded cache. The Small profile peaks at +19 MiB over the
bare process (3 MB page-cache budget), about 0.5 % of 4 GB; the default peaks at +47 to +54 MiB
(about 1.1 to 1.3 %). Model memory, not the store, decides whether 4 GB works. The things that
could have made it harder were measured and refused: mmap (+87 MiB warm, +150 MiB peak at 100k
rows) is off, and the per-connection caches are split rather than multiplied. Watch items for
later tasks, not blockers: FTS5 indexing throughput (about 10k rows/s) bounds ingestion speed, so
M2-08 should batch and yield to the priority classes, and large single-index BM25 queries need the
candidate caps noted above.

## Re-evaluation trigger
- The first 4 GB emulated run (the `experimental-4g` profile): re-measure the Small profile inside
  the 4 GB container and relabel these figures as **emulated**.
- M2-08 ingestion benchmarks: if FTS5 insert throughput (9.4k to 16.5k rows/s here) or the
  translated driver is the bottleneck rather than the single writer, reopen ADR 0009 (the reversal
  seam is `internal/store` alone).
- A `modernc.org/sqlite` or SQLite upgrade (security fixes arrive only that way): rerun
  `TestMemoryFootprint` and the FTS5 tests, and check whether the false integrity finding on a warm
  FTS5 connection still reproduces.
- A corpus above about 100k rows per FTS index, or a BM25 p95 target that 192 to 208 ms misses:
  revisit per-tenant FTS partitioning and candidate caps with the RAG task.
