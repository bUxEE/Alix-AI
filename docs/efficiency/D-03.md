# Efficiency review — D-03: DecisionModelProvider contract, candidate guard, gates, cache, audit, fake scorer

Every feature records this before it counts as done.

All timings below are **dev-box numbers**, not target-host numbers: Intel i7-10700K, Windows 11, Go 1.27.1, one
process, `go test -bench . -benchtime=20000x ./internal/decision/` (`bench_test.go`). They are labelled
**emulated-by-construction**: no model runs here, the scorer is the instant fake, and the audit appender is an
in-memory double (a real append is one SQLite transaction, measured by the audit task, not here).

## Requirement
The layer must be able to skip the controller for bounded decisions without ever deciding anything itself: guard the
candidate set before a scorer sees it, accept a result only through typed gates, re-resolve every selection through the
deterministic adapter, and add negligible CPU, RAM and latency of its own. With the layer off or failing the system must
behave exactly as without it.

## No-model / deterministic option
This is the first option and it stays the default. The exact-rule router is a normalised string lookup in a phrase
table (the shape of dialogue's control detectors for confirm, reject, cancel, help, exact capability names and ids):

| Path | ns/op | B/op | allocs/op |
|---|---|---|---|
| exact-rule lookup (`BenchmarkExactRuleRouter`, 7-phrase table) | 88 | 8 | 1 |

It resolves the obvious cases with no model, no resident memory and no model latency, and it is the fallback for every
failure of the scorer, so it is not removed or weakened by this task. D-04 owns the rules and measures them against the
controller-only path on the conversation corpus. The scorer is justified only for the cases the rules cannot decide:
choosing one item from a short authorised list, or a path among already-authorised actions, from free text.

## Candidates evaluated
No scorer model is evaluated in this task; D-03 builds the guard and the contract every candidate plugs into. What this
task does measure is the cost the guard adds around any candidate, for an 8-candidate set (the typical case; the cap is
16):

| Candidate | Size | Peak RSS | p50 / p95 | Quality | Licence | Verdict |
|---|---|---|---|---|---|---|
| exact-rule router | none | none | 88 ns | exact cases only | n/a | default, first |
| guard: structure + resolver calls + shape (`BenchmarkGuard`) | code | 256 B/op, 2 allocs | 1.8 us | n/a | project | always on |
| acceptance gates (`BenchmarkGate`) | code | 0 allocs | 0.11 us | n/a | project | always on |
| whole engine, cache miss, instant fake scorer (`BenchmarkScoreMiss`) | code | 1.7 KB/op, 26 allocs | 15 us | n/a | project | measured |
| whole engine, cache hit (`BenchmarkScoreCacheHit`) | code | 1.2 KB/op, 21 allocs | 11.7 us | n/a | project | measured |
| smaller qualified scorer, CLM-v0.1-8B | not measured | not measured | not measured | not measured | see model registry | evaluated by later D tasks and `tools/decbench` |

The 11-15 us whole-engine figure is dominated by building and hashing the audit payloads and the cache key (the
fake appender is a mutex and a `Sprintf`); the guard itself is under 2 us. None of these numbers says anything about a
scorer's speed, safety or quality, and no vendor claim about CLM is made or repeated here.

## Decision
Keep the deterministic rules first and the scorer optional. The guard, gates, cache and audit are always-on code with a
cost around 15 us per scoring request on the dev box, three orders of magnitude below any model call. Rejected: running
the gates inside the provider (it would let each provider decide its own acceptance); a background cache-eviction
goroutine (the cache is bounded FIFO and expires entries on read with the injected clock, so it owns no goroutine);
calling `Exposed` once per candidate lazily after the model (it would let the scorer see unauthorised candidates).

What a scorer call must save to be worth it. Per turn it costs `guard + scorer latency + audit appends`, and it saves
`P(accepted) x (controller call avoided)`. It pays when

    P(accepted) x controller_call_cost  >  scorer_call_cost x (1 - cache_hit_rate) + guard_cost + audit_cost

with `guard_cost` about 2 us and engine overhead about 15 us here, so the decision is made by the scorer's own latency
and acceptance rate against the controller's latency and tokens for the same turn. Those two numbers are not measured in
this task; D-04 counts controller calls and generated tokens avoided and the D benchmark matrix measures the scorer on the
target host. A scorer that does not beat the exact rules plus the controller on that comparison stays off.

## Resource impact
- CPU: about 15 us per uncached request, about 12 us per cached request (audit payloads dominate); guard 1.8 us;
  gates 0.11 us. Dev-box, emulated.
- RAM: the cache holds at most `CacheEntries` results (default 256, each a few hundred bytes plus its key) for
  `CacheTTL` (default 30 s); no goroutines, no timers, no model resident. A request allocates about 1.7 KB.
- Storage: three to four small audit events per scored turn (invoked, accepted or fallback, final action), identifiers
  and numbers only, no labels or text. Disabled: zero events from the decision path when the caller does not call it.
- Latency: bounded by `min(request deadline, Config.Timeout)` (default 250 ms), after which the call is a timeout and the
  deterministic path continues.
- Concurrency: the engine is stateless apart from the mutex-protected cache; a provider call is synchronous on the
  caller's goroutine, so concurrency is whatever the caller already has.

## 4 GB profile impact
Preserves it. Nothing here loads a model or starts a service; the layer is off by default (`Config` zero value), a Lite
or 4 GB deployment runs the exact rules and the controller exactly as before, and the cost of the guard code is
negligible in RAM. Whether any scorer fits the 4 GB profile is decided by the later benchmark tasks, not by this one.

## Re-evaluation trigger
A scorer candidate enters the model registry (D-05 onward) and needs its real latency and acceptance rate set against
the formula above; the conversation corpus of D-04 changes the share of turns the rules already resolve; or the real
audit log's append cost (SQLite transaction) turns out to dominate the per-turn cost, in which case the
accepted-result and final-action events can be batched.
