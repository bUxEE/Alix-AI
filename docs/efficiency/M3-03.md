# Efficiency review — M3-03: bounded context assembly and history compaction

Every feature records this before it counts as done.

All figures were measured on the Windows 11 dev box (Intel i7-10700K, 16 logical CPUs) with Go 1.27,
`CGO_ENABLED=0`, SQLite (`modernc.org/sqlite`) on the box's temp disk, and are labelled **dev box**:
they are not from a resource-limited container, so they are neither **emulated** nor **certified**.
**No model runs in this task.** Every figure about prompt size is in `providers.EstimateTokens` units
(one token per three bytes, rounded up; it overestimates English and Italian by about a third, which
fails closed) and is computed from the real prompts the builder produces, from a conversation driven
through the real `sessions.Store`. Anything about inference time, KV memory or the quality of a
summary or an embedding is an **estimate from arithmetic, not a measurement**, and is labelled so. The
conversation is synthetic (a library application, nine canned user phrases, a goal started, filled and
completed every few turns, goals set aside and resumed): it exercises the bounds, it does not measure
how well a model answers from the context.

Repeat the measurements:

```
go test -count=1 -run 'TestLongHistory500TurnsBounded|TestLongHistoryEveryProfile' -v ./internal/dialogue/context/   # tokens at turn 5/50/500, heap
go test -run xxx -bench . -benchmem -benchtime 1000x -count 5 ./internal/dialogue/context/                           # cost of the context path
go test -count=1 -cover ./internal/dialogue/context/                                                                 # 12 test functions, 94.0 % of statements
```

## Requirement
§11.3: the model's context is the session state (active and suspended goals, slots with their origins,
the pending clarification, bounded relevant turns, compact completed-goal capsules); "the full
transcript is stored separately from the model context. Old turns are not repeatedly replayed."
§17.2: "one bounded context per active request; capped prompt, output and tool-schema tokens".
§21 M3 exit criterion: "long-history tests preserve bounded prompt and memory use". For this task:

- a context builder with a **hard token budget per profile**, enforced before the runtime is called,
  and a separate cap on everything that derives from history, so history cannot eat the budget however
  large the total is (SEC-076);
- **deterministic compaction**: completed-goal capsules and relevant-turn selection, no model
  summarisation unless this review justifies it;
- a **500-turn test**: prompt size and process memory stay within budget, measured at turn 5, 50 and
  500, with the heap growth recorded;
- safety, unchanged by compaction: everything a user, a host or a document wrote is fenced data and
  never a system message (§12.6); the scope, a preparation, a receipt or a goal ID never reaches a
  prompt; the model sees only what the policy projection lets it see (rule 6); the context path never
  reads the transcript.

## No-model / deterministic option
**Chosen, and sufficient.** `internal/dialogue/context` (package `dctx`) is plain Go over
`sessions.State`, the bounded recent window and the caller's frame:

| Mechanism | How | Bound |
|---|---|---|
| Budget per profile | `Profile` (`experimental-4g`, `lite`, `balanced`, `performance`): prompt, output, shortlist, utterance, history tokens, rows, capsules, suspended goals, slots, value length. `Profile.Budget()` is the `providers.Budget` the runtime wrapper gets, so both enforce the same numbers | an unknown profile name is an error, never a default |
| History sub-cap | `MaxHistoryTokens`: the turn rows, capsule lines and suspended lines together, whatever the total is | Lite 384 est. toks of 2,048 |
| Cut order | the selected rows that are not among the newest 2 (lowest rank first), then the capsule digest, then the oldest full capsules, then the goals set aside, then the newest rows themselves (the question being answered outlives an old completed goal); then (only if the total is still over) the offered choices, then the lowest-ranked capabilities. The goal, its slots and the user message are never cut. If the minimum does not fit, `Build` returns the same `validation_failed` budget violation the runtime boundary raises, and nothing is sent | fixed order, tested monotonic as the budget shrinks |
| Capsules | the newest 3 (Lite) render in full: capability, outcome, field names, the few values the writer chose to keep, the records. The older ones fold into **one digest line** ("5 earlier goals: loans.extend success x2; ..."), counted by (capability, outcome) and capped at 6 distinct entries. Maps are read in sorted order; no time, goal ID, receipt ID or version is rendered | digest size is flat however many capsules fold into it |
| Goals set aside | one line each (capability, why, the names of the fields collected, never the values), newest 3 | 3 lines |
| Relevant turns | of the newest `CandidateRows` (24) rows of the recent window, a row is replayed if it is one of the newest 2 rows, belongs to a turn the state points at (the turn that set a slot of the goal, or the turn of the last directive), or shares a word with this turn (message, goal capability, the field it waits for, the values it holds). Ranked recent, referenced, lexical (best score, then newest); the best 6 are kept, each clipped to 240 runes. Scoring is a set intersection over short rows: no embedding, no model, no allocation per row | 6 rows; 24 rows read |
| The transcript | unreachable: history comes only through `TurnSource`, an interface whose only method is `RecentTurns`; a test scans the package source for any reference to the transcript | none read |

What this does not solve, honestly: relevance by shared words misses a reference that uses no common
word ("the one we talked about earlier" when the earlier turn named the title and the message does
not), and the synthetic conversation cannot show how often that happens. The deterministic path
already resolves "the second one", "the same date" and "that reservation" from `State.Results`,
resolved entities and capsules (M3-02, `refs.go`), without any model context, which is where most
such references go. If a corpus run shows a real gap, the answer ranked below is a bigger lexical
window or an embedding, not a summary (Candidates).

## Decision
**Deterministic compaction with a hard budget per profile and a separate history cap; no model
summarisation; no embedding.** The measurements below hold for Lite. The smallest candidate that meets
the requirement is the one chosen, and the model-based candidates are rejected on arithmetic, not
because they were tried.

Prompt size, **Lite** (cap 2,048 est. toks, history cap 384), conversation driven through the real
`sessions.Store`, builder output after turn 5, 50 and 500:

| Turn | Est. toks | Bytes | Frame | Output constraint | Session state | Turn rows | User msg | History (cap 384) | Rows replayed | Capsules (full + digested) | Set aside | Cut by the budget |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 5 | 1,435 | 4,189 | 691 | 338 | 119 | 252 | 35 | 299 | 6 | 1 + 0 | 1 | nothing |
| 50 | 1,499 | 4,394 | 691 | 338 | 219 | 216 | 35 | 352 | 5 | 3 + 5 | 3 | one turn row (history cap) |
| 500 | 1,435 | 4,201 | 691 | 338 | 177 | 194 | 35 | 340 | 5 | 3 + 5 | 3 | one turn row (history cap) |

Over all 500 turns the largest prompt was **1,530** est. toks (cap 2,048) and the largest history part
384 (cap 384, so the sub-cap was binding and held). The prompt at turn 500 is no larger than at turn
50: the plateau is the claim, and it holds because every history section has a count and a token cap,
not because the history happens to be short. Replaying the transcript would have been 5,305 est. toks
at turn 50 and 43,505 at turn 500. Per-turn growth after the plateau: zero.

The same 500-turn run for every profile (provisional budgets, below), est. toks at turn 5, 50, 500:

| Profile | Cap | Turn 5 | Turn 50 | Turn 500 | History cap | Shortlist | Rows replayed at 500 |
|---|---|---|---|---|---|---|---|
| experimental-4g | 1,536 | 1,234 | 1,254 | 1,192 | 224 | 3 | 3 |
| lite | 2,048 | 1,435 | 1,499 | 1,435 | 384 | 5 | 5 |
| balanced | 4,096 | 1,569 | 1,736 | 1,679 | 1,024 | 5 (frame has five) | 10 |
| performance | 8,192 | 1,599 | 2,061 | 2,002 | 2,048 | 5 (frame has five) | 16 |

Sizes of the pieces: one capsule line with four kept facts and a record is 61 est. toks (182 bytes);
the digest of five older capsules is 55 est. toks (163 bytes), against about 300 for five lines; a
typical turn with no history costs 1,066 est. toks on Lite (a 5-capability frame, the constraint and
the message), which matches the 1,076 of M1-14's measurement of the same shape.

Choices the plan left open, recorded for the ADR owner:

- **The per-profile budgets are provisional.** `docs/operations/resource-budgets.md` (M0-15) had not
  merged. The Lite row is M1-14's proposal (2,048 est. prompt toks, 256 output, shortlist 5); the other
  rows are scaled from it by memory, never larger for a smaller machine (a test enforces the order).
  When M0-15 lands, replace the table in `profile.go`; nothing else changes.
- **An over-long message is rejected, not clipped.** Cutting what the user wrote changes what they
  asked; the profile's `MaxUtteranceRunes` (1,000 on Lite, the engine's own default) is a typed
  `validation_failed`, like every other budget violation.
- **Visibility is an input, and nothing is shown without it.** `Visible(capabilityID, field)` decides
  what of the state the model may see (slot values, capsule facts, the capability itself); the engine
  builds it from the policy decisions of the turn. A nil function shows no state at all.
- **The package is named `dctx`** (directory `internal/dialogue/context`), so that code importing it keeps
  the standard library's `context` under its own name, and it **does not import `internal/dialogue`**,
  so the engine can import it without a cycle. The caller owns the content (the frame and the output
  constraint as a function of the shortlist length) and the package owns layout, data flow and budget.
- **Capsule and suspended-goal lines are new context**, about 60 est. toks per full capsule and about 22
  per set-aside goal. The M1-14 engine does not show them to the model; they are the price of "a
  completed goal is remembered as a line, not as its turns" and are inside the history cap.

## Resource impact
**Dev box**, deterministic fake data, SQLite with the store's defaults:

| | Mean of 5 runs of 1,000 (range) | Allocation per op |
|---|---|---|
| `Build` only, turn 5 state | 73 to 96 us | 37 KB, 290 allocations |
| `Build` only, turn 500 state | 109 to 134 us | 50 KB, 323 allocations |
| Context path of a turn at turn 5: read the session, read the window, build | 307 to 347 us | 61 KB, 566 allocations |
| Context path of a turn at turn 500 | 457 to 577 us | 97 KB, 817 allocations |

About 18 KB and a share of the allocations of `Build` are the test's own frame renderer (a JSON
marshal of the output constraint; the real one is the engine's), so the builder alone is closer to 30
KB. The cost is dominated by the two SQLite reads (about 200 to 350 us); the builder is about a quarter
of the context path, and the whole path is under half a millisecond against model calls expected to take
hundreds of milliseconds to seconds on Lite (**estimate, not measured**). Reading the window is
`CandidateRows` (24) rows, whatever the session holds.

**Memory.** Live heap after a forced collection, whole test process, at the first run: **1.24 MiB at
turn 5, 1.27 MiB at turn 50, 1.36 MiB at turn 500; growth from turn 50 to turn 500 was 95 KiB** (eight
runs of the test: 1 to 95 KiB), against a test bound of 4 MiB. The comparison starts at turn 50 so the one-off
warm-up (SQLite page cache, regexp tables) is not counted. Nothing the builder allocates outlives the
call; the long-lived state is the session row (bounded in `internal/sessions`: 8 capsules, 3 suspended
goals, 40 recent rows of at most 2,000 runes) and, outside this package, the transcript, which this path
never reads. At turn 500 the transcript held 1,000 rows and the context path read 24 of the recent
window.

**KV cache and prompt processing** (estimate, arithmetic, not measured): a request is at most 2,048 est.
toks of prompt plus 256 of output on Lite, so the KV memory a request needs is fixed by the profile and
does not grow with the conversation. Against the 4,096-token context of the 350M rung of ADR 0020 (112
MiB at f16, one slot), a Lite request of at most 2,304 est. toks (prompt plus output) fills about 56
percent of it, and the real count is lower because the estimator overestimates.

**Storage:** nothing added; no table, no migration, no file. **Concurrency:** the builder holds no state
and is safe to call from every session in parallel. **Power:** not measured; the path is a fraction of a
millisecond of one core per turn.

## 4 GB profile impact
**Preserves** the 4 GB direction and makes one of its levers concrete; it is not evidence that 4 GB
works (that stays aspirational until the full workload passes its gates).

- Context cannot grow with conversation length: every history section has a count and a token cap, so
  KV memory per request is fixed by the profile. The `experimental-4g` row (1,536 est. toks, shortlist
  3, 4 replayed rows) keeps the 500-turn prompt at 1,192 est. toks.
- No resident model, process, listener or table is added; no embedding is loaded for this. A model
  summariser would have added a second pass through the one resident model (CPU, latency) or a second
  model (memory); it was rejected for that reason too.
- The per-turn heap is transient (about 50 KB) and the heap does not grow with history (1 to 95 KiB over 450
  turns, across eight runs: noise).
- The risk is not memory: the 4 GB row of the budget table is a proposal from this task, not a value
  derived from a 4 GB run, and a 1,536-token prompt may be too small for a package whose frame alone is
  large (the fixture frame with constraint is 916 est. toks at three capabilities). M0-15 owns the
  number; if the minimum does not fit, the builder fails with a typed budget violation and sends nothing.

## Re-evaluation trigger
- **M0-15 publishes `docs/operations/resource-budgets.md`**: replace the provisional table in
  `internal/dialogue/context/profile.go` with its token caps, and re-run the figures above.
- **The engine adopts the builder** (a later M3 or M4 task): re-measure the real frame (the fixture's is
  691 est. toks of system text and 338 of constraint) and the real policy `Visible`, and check that the
  engine's `MaxRecentTurns`/`MaxTurnRunes` are replaced by the profile, not added to it.
- **The first M1 conversation corpus run against a real controller model**: replace the estimated tokens
  with the runtime's counts, and measure how often a reference is lost that a larger window, an
  embedding-ranked window or a longer capsule would have kept. Only that measurement can justify an
  embedder or any summarisation; until then both stay rejected.
- **RAG evidence entering the prompt** (M2-10 and later): its budget is separate and has to be added to
  this one; the history cap may need to shrink.
- **A new language pack**: the stopword list and the bytes-per-token ratio are English and Italian.
