# Disaster-recovery drill: evidence report

Status: generated by the drill itself on 2026-10-03 (task M6-04). Every figure and every observation below was written by the run that produced this file; none was typed in.
The guide that uses this evidence is [`docs/operations/production.md`](../../operations/production.md).

**Label: emulated.** One Windows 11 development machine, small data volumes, test keys and no model. These are not measurements of the Lite or Balanced profile, of a packaged install, or of any real host, and
nothing here certifies a profile. The report says what was run, what was seen, and what was not covered.

## 1. What was run

- **The program.** `alixai` was built from this checkout (`CGO_ENABLED=0`, as shipped). Every operator step (`package keygen`, `package sign`, `trust add-key`, `keys init`, `package install`,
  `identity add-issuer-key`, `audit run`, `audit accept-warning`, `backup create`, `backup verify`, `backup restore`, `upgrade status`, `upgrade recover`, `upgrade apply`, `trust list`, `trust revoke-key`)
  is that binary's own command line, run as a subprocess against a throw-away data directory in a temporary directory. The service is a real `alixai serve` process whose PID the test holds. It is stopped
  with a hard kill (TerminateProcess on Windows): no handler runs, no checkpoint is signed, and SQLite's `-wal` and `-shm` files stay behind.
- **The application.** The clinic-booking reference application runs as a node subprocess (test support mode, a loopback port it picks). AlixAI reaches it over MCP through the signed package's own endpoint, and
  every claim about what the application was asked to do is made on the application's own counters.
- **The injection point.** A loopback proxy between AlixAI and the application. The package is signed with the proxy's address as its endpoint. The proxy passes everything through, except that it can hold one named
  tool call, so that the service can be killed while that call is in flight: before the application has seen it, or after the application applied it and before the reply came back.
- **What was seeded in-process, and why.** `alixai serve` starts its inference path only from a model file whose SHA-256 matches the registry (SEC-063) and has no seam for another provider, so no turn through the
  binary can produce a preparation on a machine without the model. The drill makes the preparation the way the dialogue engine does after a turn, with the real action coordinator and the real MCP adapter built from the
  installed package, for a session of a real principal, before the service starts. The model only proposes, so nothing authoritative is skipped: confirmation, commit, receipt, the write-ahead
  record and recovery are the service's, over HTTP, with context tokens the application minted. The transcript the history index is built from (20 000 turns) was written by the drill in one transaction.
- **Keys.** The package is signed with the published TEST-ONLY publisher key; the audit signer and the second backup key are generated by the test; the release manifest for `upgrade apply` is signed with the
  published TEST-ONLY key and accepted with `-allow-dev-key`. No production key is involved.

## 5. What the drill found that the operator must know

1. **`alixai upgrade recover` does not look for fresh damage.** With no unfinished upgrade it rebuilds only the indexes that are already isolated, and answers `nothing_to_do` on a database whose index is corrupt;
   `upgrade status` lists only what is isolated. The command that checks every derived index and repairs the damaged ones is `upgrade apply`, which needs a signed release newer than the one installed. The guide in
   `docs/operations/guides/backup-restore.md` (section 6) says that `upgrade recover` isolates and rebuilds a damaged index; that is true only for an index an interrupted `upgrade apply` had already isolated.
2. **A killed service leaves `alixai.db-shm`, and `backup restore` and `upgrade apply` refuse until `-force` is given.** `-force` is right only after the process you started has exited. The refusal is the
   designed one and it names the file.
3. **A killed backup leaves a `<id>.partial` directory that nothing removes.** It has no manifest, does not verify and cannot be restored; the operator deletes it.
4. **A restore to a backup makes AlixAI forget what came after it, and the application does not.** In the destroyed-database case the booking made after the backup is gone from AlixAI's receipts while the
   application still holds it. The two are reconciled by comparing AlixAI's records with the application's. When the old database is readable, `pre_restore_dir` keeps it whole and holds the receipt.
5. **A revoked checkpoint key stops the service from starting** when the configuration (or the default path `<data_dir>/keys/audit-checkpoint.key`) still names it.

## 6. What this does not show

- **No model.** The inference path was off on every start (`/readyz` answers 503 naming it, by design), so no turn ran through the binary. Preparations were made in-process (section 1).
- **Hard kill only.** There was no power cut, no lost fsync, no full disk and no filesystem fault beyond the byte flips the scenarios inject. SQLite's own crash safety is relied on, not measured.
- **One host.** Windows 11 on one machine. Linux, macOS, systemd, Quadlet and the container stack were not exercised, and nothing here was run on a Lite, Balanced or 4 GB profile.
- **Small volumes, one tenant, one application.** See section 4.
- **Test keys.** No real publisher, release or checkpoint key custody was exercised, and no key was held in a KMS.
- **The application's own recovery.** The clinic application is a fixture that keeps its data in memory; backing up and restoring an application is that application's job.
- **Restore on another host, remote backup, and restore with a service still running** (a restore refuses that).

## 7. Re-run

The drill needs Go, node (22.18 or newer) and the clinic application's dependencies (`pnpm install --ignore-workspace --offline --frozen-lockfile` in `examples/reference-apps/clinic-booking`). A default
`go test` writes nothing into the repository; this report and `results.json` are written only when the whole drill runs with the evidence directory set:

```sh
go test -count=1 ./tests/dr/...
ALIXAI_DR_EVIDENCE_DIR=docs/evidence/m6-dr go test -count=1 ./tests/dr/...
```
